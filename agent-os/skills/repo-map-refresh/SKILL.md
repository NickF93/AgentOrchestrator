# repo-map-refresh

## Purpose

Provide a repeatable, execution-layer procedure for keeping a governed
repository's `REPO_MAP.md` accurate and fresh. This skill applies the
freshness policy that is already defined in canonical authorities — it
does not define, relax, or restate that policy from memory. When a rule
must be verified, read the authority file.

The freshness contract has three moving parts that already exist in the
control plane; this skill is the missing *actor* that closes the loop:

- the **template** defines the map's structure and the three freshness
  fields (`last_validated_on`, `validated_by`, `freshness_window_days`);
- the **policy** defines the staleness formula and the refresh triggers;
- the **validator** (`validate-plan.py --check-freshness`) is the hard
  gate that blocks a checkpoint from closing on a stale or unstamped map.

`plan-checkpoint-close` *consumes* freshness (it reads the gate at
closure). `repo-map-refresh` *produces* it: detect → refresh → re-verify.

The skill is **procedural and read-mostly**. It reads the live repository
to re-derive the objective sections, writes only `{repo_root}/REPO_MAP.md`,
never auto-commits, and never invents judgment content. A `REPO_MAP.md`
that does not exist yet is **not** this skill's job to create — that is
`repo-bootstrap` (which renders it from the template).

Canonical authorities (paths relative to `control_plane_root`):

- `agent-os/templates/repo-REPO_MAP.md.template` — map structure and the
  three freshness fields (default `freshness_window_days: 30`)
- `agent-os/workflow/lifecycle.md` — §"REPO_MAP Freshness Mechanism":
  staleness formula, refresh triggers, checkpoint consumption
- `agent-os/workflow/shared-workflow.md` — §"REPO_MAP.md freshness":
  ownership (orchestrator maintains; implementers/reviewers propose deltas)
- `agent-os/scripts/validate-plan.py` — `check_repo_map_freshness()`, the
  gate behind `--check-freshness`

## Two-Root Model

This skill operates with two distinct roots. Every path used in the
procedure belongs to exactly one of them.

| Root                  | What lives there                                          |
|-----------------------|-----------------------------------------------------------|
| `repo_root`           | The target governed repo: source code, tests,             |
|                       | `plan/PLAN-index.yaml`, and `REPO_MAP.md` (the file this   |
|                       | skill refreshes)                                          |
| `control_plane_root`  | The Level-0 checkout: the template, the freshness policy  |
|                       | docs, and `validate-plan.py`                              |

At Layer 0 (the control-plane repo itself) the two roots coincide, but the
control plane has no `REPO_MAP.md` of its own — this skill almost always
runs against a Layer-2 repo where the roots are different sibling
directories under a workspace parent.

### Resolving `control_plane_root`

Use the first match (same order as `workspace-sync`):

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Environment / workspace stamp**: `CONTROL_PLANE_ROOT` is set in the
   environment or stamped into the workspace runtime files generated by
   `sync-workspace.sh`.
3. **Self-detection**: if invoked from within the control-plane repo
   (the directory containing `agent-os/scripts/validate-plan.py`), derive
   from that repo root.
4. **Fail**: "Cannot locate control-plane root. Provide control_plane_root
   explicitly or export CONTROL_PLANE_ROOT."

After resolution, verify that both
`{control_plane_root}/agent-os/templates/repo-REPO_MAP.md.template` and
`{control_plane_root}/agent-os/scripts/validate-plan.py` exist. If either
is missing, fail — the control-plane checkout may be stale or incomplete.

## When to Use

Use this skill when **any** of these holds for `{repo_root}`:

- A **refresh trigger** has fired (per `lifecycle.md`):
  - a change to entry points, module boundaries, or critical interfaces;
  - a test-topology change (unit/integration/e2e layout);
  - a release or checkpoint closure;
  - a major refactor touching hot paths or fragile areas.
- `validate-plan.py --check-freshness` reports the map **stale** or with a
  **missing `last_validated_on`**.
- A checkpoint (`C`-item) is blocked from `verified → done` because the map
  is out of date.
- The repo was **just bootstrapped** and its map is still the empty template
  (blank `last_validated_on`, placeholder section stubs). A first
  post-bootstrap validation pass is a refresh trigger: a blank
  `last_validated_on` is stale by definition.

Do **not** use this skill to create a brand-new map (delegate to
`repo-bootstrap`) or to commit/push (that is the operator's step, optionally
via `gitflow-pr-only`).

## Required Inputs

| Input                | Type   | Default       | Description                                                       |
|----------------------|--------|---------------|-------------------------------------------------------------------|
| `repo_root`          | string | `.`           | Root of the target governed repository                            |
| `control_plane_root` | string | (resolved)    | Root of the Level-0 control-plane checkout                        |
| `validated_by`       | string | (required when writing) | Identifier stamped into `validated_by` (agent or person) |
| `trigger`            | string | (optional)    | Which refresh trigger fired (entry-points / interfaces / tests / release / refactor); recorded in the report |
| `dry_run`            | bool   | `false`       | If true, compute and report all deltas and the metadata that would be written, but write nothing |

## Expected Outputs

A structured refresh report:

```
verdict: fresh | refreshed | dry-run | blocked | fail
repo_root: <path>
control_plane_root: <path>
trigger: <trigger or none>
staleness:
  last_validated_on: <date or none>
  freshness_window_days: <int>
  age_days_before: <int or n/a>
  stale_before: true | false | unknown
  age_days_after: <int or n/a>
  stale_after: true | false | n/a
proposed_section_deltas:
  objective:                       # re-derived mechanically
    entry_points: <added/removed/unchanged + values>
    main_modules: <added/removed/unchanged + values>
    test_map:     <added/removed/unchanged + values>
  judgment:                        # proposed, await operator confirmation
    hot_paths:     <candidate deltas or none>
    fragile_areas: <candidate deltas or none>
metadata_stamp:
  last_validated_on: <old> -> <new or unchanged>
  validated_by:      <old> -> <new or unchanged>
freshness_recheck:
  command: `validate-plan.py <repo>/plan/PLAN-index.yaml --check-freshness`
  exit: <code or n/a>
  note: <gate active only when a checkpoint is in review/verified>
commands_run:
  - <command> -> exit <code>
next_steps:
  - <operator guidance: confirm judgment deltas, commit, etc.>
```

## Procedure

Execute in order. Stop and report on the first blocking failure unless all
issues can be enumerated without side effects (then collect them first).
The ordering matters: **re-derive and confirm content before stamping
freshness** — stamping `last_validated_on` is an assertion that the map was
actually re-verified today, so it must come last.

### Step 0 — Resolve roots and tooling

1. Resolve `control_plane_root` using the order above.
2. Verify the template and `validate-plan.py` exist under it.
3. Record both roots in the report header.

### Step 1 — Locate the map

1. Check whether `{repo_root}/REPO_MAP.md` exists.
2. If it is **missing**, stop with verdict `blocked` and point the operator
   to `repo-bootstrap` (which renders `REPO_MAP.md` from the template). Do
   not fabricate a map — a map with no provenance is worse than none.

### Step 2 — Read current freshness metadata and compute staleness

1. Parse the header fields from `{repo_root}/REPO_MAP.md`: `last_validated_on`,
   `validated_by`, `freshness_window_days` (default to 30 if absent, matching
   the validator).
2. Compute staleness with the canonical formula:
   `stale ⇔ today - last_validated_on > freshness_window_days`.
   A missing/empty `last_validated_on` counts as stale (the validator treats
   it as a hard failure at checkpoint boundaries).
3. Record `age_days_before` and `stale_before` in the report. If the map is
   already fresh and no `trigger` was supplied, you may stop early with
   verdict `fresh` (no rewrite needed) — report the age and the window.

### Step 3 — Re-derive the objective sections (mechanical)

Inspect the live repository read-only (Glob / Grep / Read) and re-derive the
three sections that can be determined from the code itself. Report each as
added / removed / unchanged relative to the current map. **Never guess** — if
a section cannot be determined, say so and leave it for the operator.

- **Entry Points** — the program's ways in:
  - main app entry (e.g. `__main__.py`, `main.go`, `src/index.*`, `app.*`,
    a `cmd/` directory);
  - CLI entry (a `bin/` dir, shebang scripts, `console_scripts` /
    `[project.scripts]`, `package.json` `"bin"`);
  - API/server entry (server bootstrap, route registration, a WSGI/ASGI
    app object, an HTTP listener).
- **Main Modules** — top-level source packages/directories, excluding tests,
  vendored code, and build output. The template seeds three slots
  (`module_a/b/c`); real maps may list more — add as many as the repo has.
- **Test Map** — unit / integration / end-to-end test locations
  (`tests/`, `test/`, `**/__tests__/`, `*_test.*`, `spec/`, language-specific
  conventions).

Two derivation details that matter, especially right after bootstrap:

- **Placeholder blanks vs. factual blanks.** The template seeds stub labels
  (`module_a`/`module_b`/`module_c`, `hot_path_1`, `fragile_area_1`). When you
  re-derive, replace those stub labels with the real findings, and where a
  section genuinely has nothing (e.g. a governance-only repo with no `src/` or
  `tests/`), record it explicitly as "none" — a factual blank is information,
  a leftover stub label is noise. Never leave `module_a:` style placeholders in
  a validated map.
- **No source/tests is a valid result.** If the repo has no detectable entry
  points, modules, or tests yet, that is the correct, honest answer — report
  "none", do not invent structure to fill the template.

### Step 4 — Propose deltas for the judgment sections (no fabrication)

`Hot Paths` and `Fragile Areas` require human judgment and cannot be inferred
reliably from static structure. Surface **candidate** deltas for operator
confirmation; do not write fabricated entries. Useful signals to *propose*
from (not to assert): high-churn files (`git log` frequency), files with many
dependents, dense `TODO`/`FIXME`/`HACK` clusters, and whatever the existing
map already records. Mark every judgment delta as "proposed — confirm".

When the signals are absent — a freshly bootstrapped or single-commit repo has
no churn history, and a structure-only repo has no clear hot paths — do not
manufacture proposals. Record the judgment sections as "undetermined — no basis
for a proposal yet; populate once the repo accrues history" and move on. An
empty, honest judgment section is correct; a guessed one is a liability.

### Step 5 — Apply confirmed updates and stamp freshness

Only after the objective sections are re-derived and any judgment deltas are
confirmed:

1. Write the confirmed section updates into `{repo_root}/REPO_MAP.md`.
2. Stamp `last_validated_on: <today>` (ISO `YYYY-MM-DD`) and
   `validated_by: <validated_by input>`.
3. Leave `freshness_window_days` unchanged unless the operator explicitly
   adjusts it.

If `dry_run` is `true`, **skip all writes**: report the section deltas and the
exact metadata that *would* be stamped, and set the verdict to `dry-run`.

### Step 6 — Re-verify against the freshness gate

1. Re-run the validator's freshness check against the target repo's plan:
   ```bash
   $AGENT_PYTHON {control_plane_root}/agent-os/scripts/validate-plan.py \
     {repo_root}/plan/PLAN-index.yaml \
     --schema {control_plane_root}/agent-os/schemas/plan.schema.json \
     --check-freshness
   ```
   The validator derives the repo it inspects from the **plan path**
   (`index_path.parent.parent`), so it reads `{repo_root}/REPO_MAP.md`.
2. **Know what the gate does**: `check_repo_map_freshness()` only hard-fails
   when the plan has a checkpoint (`C`-item) in `review` or `verified`. With
   no active checkpoint, a fresh exit-0 does **not** prove the map is fresh —
   it proves the gate had nothing to block. Therefore always report the
   **direct staleness computation** from Step 2/Step 5 as the primary
   evidence, and the validator exit as confirmation that the closure gate is
   (or is not) satisfied.
3. Set the verdict: `refreshed` (map written and now within window),
   `fresh` (was already within window, no write needed), `dry-run`,
   `blocked` (missing map / unresolved control plane), or `fail` (the gate
   still reports stale after a refresh — e.g. a malformed date was written).

## Worked Example: Dry-Run Refresh

A small downstream repo `acme-widgets/` was bootstrapped 45 days ago and its
map has not been touched since. Its window is the default 30 days, so it is
stale. The operator runs `repo-map-refresh` with `dry_run: true` and
`validated_by: orchestrator` after merging a refactor that split the CLI out
of the core package.

Current `acme-widgets/REPO_MAP.md` header (illustrative):

```
last_validated_on: 2026-04-16
validated_by: orchestrator
freshness_window_days: 30
...
## Entry Points
- Main app entry: src/widgets/__main__.py
- CLI entry:
- API entry:
## Main Modules
- module_a: src/widgets/core
- module_b:
- module_c:
## Test Map
- unit tests: tests/unit
- integration tests:
- end-to-end tests:
```

**Step 2 — staleness**: `today (2026-05-31) - 2026-04-16 = 45 days > 30` →
`stale_before: true`, `age_days_before: 45`.

**Step 3 — objective re-derivation** (from the live tree):

```
entry_points:
  - Main app entry: src/widgets/__main__.py        (unchanged)
  - CLI entry: src/widgets/cli/main.py             (ADDED — new after refactor)
  - API entry: src/widgets/api/server.py           (ADDED)
main_modules:
  - module_a: src/widgets/core                     (unchanged)
  - module_b: src/widgets/cli                      (ADDED)
  - module_c: src/widgets/api                      (ADDED)
test_map:
  - unit tests: tests/unit                         (unchanged)
  - integration tests: tests/integration           (ADDED)
  - end-to-end tests:                              (still none — report, do not invent)
```

**Step 4 — judgment deltas (proposed, await confirmation):**

```
hot_paths:     proposed: src/widgets/core/dispatch.py (highest churn, 22 commits/30d) — confirm
fragile_areas: proposed: src/widgets/api/server.py (new, no integration coverage) — confirm
```

**Step 5 — metadata that WOULD be stamped (dry-run, not written):**

```
last_validated_on: 2026-04-16 -> 2026-05-31
validated_by: orchestrator -> orchestrator
freshness_window_days: 30 (unchanged)
```

**Step 6 — re-verify (what the real run would show):** before the refresh,
with an active checkpoint, the gate fails:
`REPO_MAP.md is stale (45 days old, window is 30 days); active checkpoint(s)
C7.2.3 cannot close until map is refreshed`. After a real (non-dry-run)
refresh stamps today's date, the same command exits 0. In dry-run, no file
changed, so the verdict is `dry-run` and the report makes clear the gate
would still fail until the operator re-runs without `dry_run`.

**next_steps**: confirm the two proposed judgment deltas; re-run without
`dry_run` to write the map; commit `REPO_MAP.md` (the skill does not commit).

## Constraints

- **Procedural only**: applies the existing freshness policy; never
  redefines the formula, the triggers, or the window. The template and
  `lifecycle.md` are the authority.
- **Two-root integrity**: template/policy/validator come from
  `control_plane_root`; the only file written is `{repo_root}/REPO_MAP.md`.
- **No writes to the control plane**: ever.
- **Order is load-bearing**: re-derive and confirm content *before* stamping
  `last_validated_on`. Stamping a date you did not actually validate defeats
  the entire freshness contract.
- **No fabrication of judgment sections**: `Hot Paths` and `Fragile Areas`
  deltas are proposals requiring operator confirmation. Leave undetermined
  objective fields blank with a note rather than guessing.
- **Refuse to invent a missing map**: delegate creation to `repo-bootstrap`.
- **No auto-commit, no push**: the operator commits `REPO_MAP.md` (Phase A);
  routing to a branch/PR is `gitflow-pr-only`'s job.
- **`dry_run` writes nothing**: full report, zero file changes.

## Failure Handling

| Failure                                                   | Behavior                                                                 |
|-----------------------------------------------------------|--------------------------------------------------------------------------|
| Control-plane root not resolvable                         | Fail (`blocked`) with resolution instructions                            |
| Template or `validate-plan.py` missing under control plane| Fail (`blocked`) naming the missing path; checkout may be stale          |
| `{repo_root}/REPO_MAP.md` missing                         | Stop (`blocked`); delegate to `repo-bootstrap`; do not fabricate         |
| Freshness metadata unparseable / header malformed         | Report what was parsed; treat unknown fields as stale; do not guess      |
| `last_validated_on` malformed (not `YYYY-MM-DD`)          | Treat as stale (matches the validator); flag for operator correction     |
| `freshness_window_days` non-integer or absent             | Default to 30 (matches the validator); note the assumption               |
| Repo has no detectable entry points / modules / tests     | Report the section as undetermined; leave blank; never invent            |
| `validated_by` not provided but a write is requested      | Fail (`blocked`): refuse to stamp an unattributed validation             |
| Operator declines proposed judgment deltas                | Stamp only the confirmed objective updates; record the declined deltas   |
| `--check-freshness` still reports stale after refresh     | Fail (`fail`): inspect the written date (likely malformed) and re-stamp  |
| Map already within window and no trigger supplied          | Stop (`fresh`); report age vs window; no rewrite                         |
| Target repo has no `plan/PLAN-index.yaml` to re-verify     | Refresh and stamp the map; report the re-verify as `n/a` with the reason |

## Adapter Notes

### Claude

Invoked via Claude Code or Claude-based agents. Use `Glob`/`Grep`/`Read` to
re-derive the objective sections read-only, `Bash` (with `git log`) to gather
churn signals for *proposed* judgment deltas, `Edit` to stamp the map, and
`Bash` to run the `--check-freshness` re-verify. Resolve `control_plane_root`
from `CONTROL_PLANE_ROOT` or the current repo root. The report is returned as
direct text.

### Codex

Use the sandbox file-system and shell tools. Both `repo_root` and
`control_plane_root` must be reachable in the sandbox (typically siblings
under the workspace). The same inspection commands and the same
`validate-plan.py --check-freshness` invocation apply.

### Gemini
