# plan-checkpoint-close

## Purpose

Provide a repeatable, execution-layer procedure for closing `C`-type
checkpoint items and their owning `commit_group`. This skill does not define
governance rules. It applies the rules already defined in the canonical
authorities, reducing operator mistakes at closure time.

This skill runs at any layer governed by the control plane:

- **Layer 0**: the control-plane repo itself — tooling and data are both local.
- **Layer 2**: any bootstrapped repo — the skill reads data from the target
  repo and runs shared tooling from the Layer-0 checkout.

This skill is procedural. All normative rules it enforces are defined in
canonical authorities. When a specific rule must be verified, read the
relevant file — do not invent or restate governance rules from memory.

Canonical authorities (paths relative to `control_plane_root`):

- `AGENTS.md` — also present locally at Layer 2 (bootstrapped copy)
- `agent-os/workflow/shared-workflow.md`
- `agent-os/workflow/lifecycle.md`
- `agent-os/workflow/git-automation-policy.md`
- `agent-os/workflow/item-taxonomy.md`

Shared asset companions for this skill:

- prompt: `checkpoint-closure-review`
- result protocol: `check-result-v1`
- profiles: `claude/check-medium`, `codex/check-medium`,
  `gemini/check-medium`, `cursor/check-medium`, `kilo/check-medium`,
  `copilot/check-medium`

## Two-Root Model

This skill operates with two distinct roots. Every path used in the
procedure belongs to exactly one of them.

| Root                  | What lives there                                        |
|-----------------------|---------------------------------------------------------|
| `repo_root`           | The target repository: `plan/PLAN-index.yaml`,         |
|                       | `REPO_MAP.md`, `AGENTS.md` (local copy), repo tests, repo code |
| `control_plane_root`  | The Level-0 checkout: shared scripts, schemas,          |
|                       | canonical workflow files, skill definitions             |

At Layer 0, both roots point to the same directory.
At Layer 2, they are different directories (typically siblings under a
workspace parent).

### Shared tooling (from `control_plane_root`)

- `{control_plane_root}/agent-os/scripts/validate-plan.py`
- `{control_plane_root}/agent-os/scripts/render-plan.py`
- `{control_plane_root}/agent-os/schemas/plan.schema.json`

### Target repo data (from `repo_root`)

- `{repo_root}/plan/PLAN-index.yaml` (or `plan_path` if overridden)
- `{repo_root}/REPO_MAP.md`
- `{repo_root}/AGENTS.md`
- Repo-specific tests and checks declared in item `checks` arrays

## Required Inputs

| Input                  | Type   | Default       | Description                                      |
|------------------------|--------|---------------|--------------------------------------------------|
| `checkpoint_item_id`   | string | (required)    | ID of the target C-type item (e.g. `C1.1.3`)    |
| `plan_path`            | string | `plan/PLAN-index.yaml` | Path to the canonical plan entrypoint (relative to `repo_root`) |
| `repo_root`            | string | `.`           | Root of the target repository                    |
| `control_plane_root`   | string | (resolved)    | Root of the Level-0 control-plane checkout       |
| `allow_commit`         | bool   | `false`       | If true, execute the commit; otherwise dry-run   |

## Resolving `control_plane_root`

Use the first match:

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Workspace-first discovery**: use `CONTROL_PLANE_ROOT` if it is available
   as an environment variable or stamped into the workspace runtime files
   generated by `sync-workspace.sh`.
3. **Local detection**: if `agent-os/scripts/validate-plan.py` exists
   relative to `repo_root`, the target repo is itself the control plane.
   Set `control_plane_root = repo_root`.
4. **Fail**: "Cannot locate control-plane root. Provide control_plane_root
   explicitly, export CONTROL_PLANE_ROOT, or run sync-workspace.sh to stamp
   the workspace."

After resolution, verify that
`{control_plane_root}/agent-os/scripts/validate-plan.py` exists.
If it does not, fail — the control plane checkout may be stale or missing.

## Expected Outputs

A compact closure report containing the fields required by `check-result-v1`:

- verdict
- findings
- evidence
- commands_run
- ready_to_close
- optional proposed_commit_message
- optional follow_up

Output template (adapt to context):

```
verdict: pass | fail | blocked
findings:
  - <finding or explicit none>
evidence:
  - repo_root: <path>
  - control_plane_root: <path>
  - commit_group: <cgNN>
  - items: <item_id_1>, <item_id_2>, ...
commands_run:
  - `python <cp>/agent-os/scripts/validate-plan.py <plan> --schema <cp>/agent-os/schemas/plan.schema.json` -> exit 0
  - `python <cp>/agent-os/scripts/render-plan.py <plan>` -> exit 0
ready_to_close: true | false
proposed_commit_message: |
  <type>(<scope>): <description>

  Summary: ...
  Scope: ...
  Items: ...
  Validation: ...

  Refs: <item IDs>, <cgNN>
follow_up:
  - <optional next action>
```

## Procedure

Execute these steps in order. Stop and report on the first blocking failure
unless all issues can be enumerated without side effects (in which case,
collect all failures before stopping).

### Step 0 — Resolve roots

1. Resolve `control_plane_root` using the resolution order above.
2. Verify `{control_plane_root}/agent-os/scripts/validate-plan.py` exists.
3. Resolve `plan_path` to an absolute path under `repo_root`.
4. Record both roots in the closure report header.

This step must succeed before any other step runs. If the control plane
cannot be located, nothing else is meaningful.

### Step 1 — Locate and validate the target

1. Parse the canonical plan entrypoint at `{repo_root}/{plan_path}`.
2. Find the item matching `checkpoint_item_id`.
3. Confirm its `type` is `C`. If not, fail: "Target is not a C-type item."
4. Record its `commit_group`, `depends_on`, `checks`, `scope`, and `status`.

### Step 2 — Resolve the commit_group

1. Find the `commit_group` entry whose `id` matches the checkpoint's
   `commit_group` field.
2. List all item IDs declared in that commit_group's `items` array.
3. Confirm the checkpoint is a member. If not, fail:
   "Checkpoint is not in its declared commit_group."
4. Confirm no items from a *different* commit_group are being mixed in.

### Step 3 — Check item statuses

For every item in the commit_group:

1. Read its current `status` from the loaded plan.
2. Closure requires each item to be in `review`, `verified`, or `done`.
   Record any item that is not.

If any item fails this check, the commit_group is not closure-ready.
Report the failing items and their current statuses.

### Step 4 — Check dependencies

For the checkpoint item and every item in the commit_group:

1. Read `depends_on` (if declared).
2. For each dependency target, verify its status is `verified` or `done`.
   (See `{control_plane_root}/agent-os/workflow/lifecycle.md` for the
   dependency rule.)

Report any unsatisfied dependencies.

### Step 5 — Run validation tooling

Run from `repo_root`, using shared tooling from `control_plane_root`:

```bash
python {control_plane_root}/agent-os/scripts/validate-plan.py \
  {repo_root}/{plan_path} \
  --schema {control_plane_root}/agent-os/schemas/plan.schema.json
```

Record the exit code and stderr. A non-zero exit is a blocking failure.

If the checkpoint's `checks` array includes freshness-related entries, also
run:

```bash
python {control_plane_root}/agent-os/scripts/validate-plan.py \
  {repo_root}/{plan_path} --check-freshness
```

### Step 6 — Check render idempotency

Run from `repo_root`, using shared tooling from `control_plane_root`:

```bash
python {control_plane_root}/agent-os/scripts/render-plan.py \
  {repo_root}/{plan_path}
```

After rendering, check `git diff` on the generated files (`PLAN.md`,
`PLAN.dot`) inside `repo_root`. If the diff is non-empty, the generated
views were stale. This is not necessarily blocking, but flag it: the render
output should be included in the commit.

### Step 7 — REPO_MAP freshness (if applicable)

If the target repository contains `{repo_root}/REPO_MAP.md`:

1. Read `last_validated_on` and `freshness_window_days` from its metadata.
2. Compute whether the map is stale (today - last_validated_on >
   freshness_window_days).
3. If stale, this blocks checkpoint closure per the lifecycle freshness
   gate. Report it.

If `REPO_MAP.md` does not exist in the target repo, this check is N/A.

(See `{control_plane_root}/agent-os/workflow/lifecycle.md` § REPO_MAP
Freshness Mechanism for the authoritative rule.)

### Step 8 — Run repo-local checks

For each item in the commit_group that declares a `checks` array:

1. List each check description.
2. Determine whether the check can be run programmatically:
   - Shared-tooling checks (e.g. "validate-plan.py exits 0") — already
     covered by Step 5; reference that result.
   - Repo-local checks (e.g. "unit tests pass", "lint clean") — run them
     from `repo_root` using the repo's own test commands.
   - Manual checks — list them as "requires operator confirmation."
3. Record pass/fail for each.

The distinction matters: shared tooling comes from `control_plane_root`,
repo-local tests come from `repo_root`. Do not confuse the two.

### Step 9 — Assemble verdict

If all checks pass: verdict is **READY**.
If any check fails: verdict is **BLOCKED** with the list of blocking
findings.

### Step 10 — Prepare commit message

This step is mandatory when the verdict is READY. Every closure-ready
checkpoint must produce a fully-formed commit message before proceeding.

Build the commit message following the contract in `{repo_root}/AGENTS.md`
(the target repo's local copy):

- Header: `<type>(<scope>): <description>`
  - `type`: typically `chore` or `docs` for checkpoint closure; infer from
    the items being closed.
  - `scope`: derive from the items' `scope` fields. If multiple scopes,
    use the broadest common prefix or the most representative one.
  - `description`: concise summary of what the commit_group achieved.
- Body: include Summary, Scope, Items, and Validation sections. The body
  is not optional — checkpoint closures touch multiple items and the commit
  record must be self-contained enough for audit.
- Footer: `Refs: <all item IDs in the commit_group>, <commit_group ID>`
- The proposed message MUST NOT include signatures, trailers, or attribution
  text traceable to generative AI or code generation. Remove any auto-added
  `Co-Authored-By:`, `Co-authored-by:`, `Generated by`, or `Generated with`
  line when it names an AI model, vendor, or code-generation tool. Legitimate
  human co-author trailers remain allowed.

The proposed commit message MUST appear in the closure report regardless
of the `allow_commit` setting. In dry-run mode, it serves as the
ready-to-use artifact the operator will commit with. Omitting it defeats
the purpose of the skill.

### Step 11 — Commit or report

- If `allow_commit` is `false` (default): output the closure report with
  the proposed commit message. Do not stage or commit.
- If `allow_commit` is `true`: stage the relevant files in `repo_root`,
  create the commit with the prepared message, and report success or
  failure. Do not push. Pushing is a Phase B operation.

## Constraints

- **Procedural only**: this skill applies existing governance rules. It
  must not define, redefine, or silently alter any rule. When in doubt,
  read the canonical authority file from `control_plane_root`.
- **Two-root integrity**: never run Layer-0 scripts from the wrong path,
  never read target repo data from the control plane, and never confuse
  which root a file belongs to.
- **Single commit_group**: never mix items from different commit_groups
  in one closure operation.
- **No auto-commit by default**: the default mode is dry-run. Committing
  requires explicit `allow_commit: true`.
- **No push**: committing is Phase A. Pushing is Phase B and is not in
  scope for this skill unless Phase B is unlocked and the operator
  explicitly requests it.
- **Fail clearly**: when a prerequisite is not met, report the specific
  failure and stop. Do not silently skip checks or downgrade failures to
  warnings.

## Failure Handling

| Failure                                | Behavior                                                 |
|----------------------------------------|----------------------------------------------------------|
| Control plane root not resolvable      | Fail with resolution instructions                        |
| Control plane scripts missing          | Fail with "validate-plan.py not found at <path>"         |
| `checkpoint_item_id` not found         | Fail with "Item not found in plan"                      |
| Target is not C-type                   | Fail with "Target is not a C-type checkpoint item"       |
| Item not in its declared commit_group  | Fail with "Checkpoint not in commit_group <cgNN>"        |
| Items not in review/verified/done      | Block; list items and their current statuses             |
| Unsatisfied dependencies               | Block; list dependency targets and their statuses        |
| validate-plan.py non-zero exit         | Block; include stderr output                             |
| REPO_MAP stale at checkpoint closure   | Block; report staleness delta                            |
| Repo-local checks fail                 | Block; include test output                               |
| Item checks not satisfiable            | Block; list unverifiable checks                          |
| Plan parse error                       | Fail with parse error details                            |

## Common-Case Command Sequence

For a Layer-2 repo where the control plane lives alongside it in a
workspace:

```bash
# Variables (resolve once)
CP="/path/to/AgentOrchestrator"       # control_plane_root
REPO="/path/to/MyProject"             # repo_root

# 1. Validate the plan (shared tooling, repo data)
python "$CP/agent-os/scripts/validate-plan.py" \
  "$REPO/plan/PLAN-index.yaml" \
  --schema "$CP/agent-os/schemas/plan.schema.json"

# 2. Freshness check (if applicable)
python "$CP/agent-os/scripts/validate-plan.py" \
  "$REPO/plan/PLAN-index.yaml" --check-freshness

# 3. Render plan views (shared tooling, repo data)
python "$CP/agent-os/scripts/render-plan.py" "$REPO/plan/PLAN-index.yaml"

# 4. Check for render drift (in repo)
git -C "$REPO" diff PLAN.md PLAN.dot

# 5. Run repo-local tests (in repo)
cd "$REPO" && <repo test commands>

# 6. Stage and commit (only if all checks pass and allow_commit is true)
cd "$REPO"
git add <plan files updated in commit_group> PLAN.md PLAN.dot <other files in commit_group>
git commit -m "<prepared message>"
```

For Layer 0 (control plane closing its own checkpoint), replace both
`$CP` and `$REPO` with the same path.

## Adapter Notes

### Claude

When invoked via Claude Code or Claude-based agents, this skill can use
`Read` to parse the canonical plan entrypoint from `repo_root`, `Bash` to run shared
validation/render scripts from `control_plane_root` against the target
repo's data, and `Grep`/`Glob` to locate REPO_MAP.md and discover
repo-local test commands. The closure report is returned as direct text
output. For control plane resolution, read the workspace `AGENTS.md` in
the parent of `repo_root` and extract the `Control plane:` line.

### Codex

When invoked via Codex agents, use the file system and shell tools
available in the sandbox. Both `repo_root` and `control_plane_root` must
be accessible within the sandbox filesystem. If the workspace layout
places them as siblings, both should be mounted.

### Kilo

When invoked via Kilo, the skill is referenced from
`.kilocode/rules/governance.md` in bootstrapped repositories. Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. Run the same shared validation/render
tooling from `control_plane_root` against the target repo.

### Copilot

When invoked via GitHub Copilot agents, the skill is referenced from
`.github/copilot-instructions.md` (the thin repo-local entrypoint).
Control plane resolution uses the workspace layout or explicit
configuration. The same closure procedure applies.

### Gemini

referenced from `GEMINI.md` (the thin repo-local entrypoint). Resolve

### Cursor
