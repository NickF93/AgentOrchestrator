# repo-bootstrap

## Purpose

Provide a repeatable, execution-layer procedure for bootstrapping
governance files into a target repository. This skill wraps the existing
`bootstrap-repo.sh` script with pre-flight validation, post-bootstrap
verification, and structured reporting. It does not define governance
rules. It applies the bootstrap process already implemented in canonical
tooling and ensures the result meets governance expectations.

This skill operates between Layer 0 and Layer 2:

- **Layer 0 (source)**: the control-plane repo provides the bootstrap
  script, templates, validation tooling, and schema.
- **Layer 2 (target)**: the repository being bootstrapped receives the
  rendered governance files.

This skill is procedural. All normative rules it enforces are defined in
the canonical tooling and templates. When a specific rule must be
verified, read the relevant file — do not invent or restate governance
rules from memory.

Canonical authorities (paths relative to `control_plane_root`):

- `agent-os/scripts/bootstrap-repo.sh` — the wrapped bootstrap script
- `agent-os/templates/` — source templates for all rendered files
- `agent-os/scripts/validate-plan.py` — post-bootstrap canonical plan validation
- `agent-os/schemas/plan.schema.json` — PLAN schema for validation
- `agent-os/workflow/shared-workflow.md` — three-layer model, workspace
  topology

## Two-Root Model

This skill operates with two distinct roots. Every path used in the
procedure belongs to exactly one of them.

| Root                  | What lives there                                        |
|-----------------------|---------------------------------------------------------|
| `repo_root`           | The target repository being bootstrapped: receives      |
|                       | AGENTS.md, ARCHITECTURE.md, REPO_MAP.md, plan/,        |
|                       | README.md, CLAUDE.md, .codex/config.toml, GEMINI.md, docs/adr/, |
|                       | .githooks/, .github/, .cursor/, .kilo/             |
| `control_plane_root`  | The Level-0 checkout: bootstrap script, templates,      |
|                       | validation tooling, schemas, skill definitions          |

For this skill, the two roots are always different directories. The
target repo is never the control plane itself (the control plane is
already bootstrapped by definition).

### Resolving `control_plane_root`

Use the first match:

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Workspace-first discovery**: use `CONTROL_PLANE_ROOT` if it is
   available as an environment variable or stamped into the workspace
   runtime files generated by `sync-workspace.sh`.
3. **Sibling detection**: if the current working directory or `repo_root`
   has a sibling directory containing
   `agent-os/scripts/bootstrap-repo.sh`, use that sibling as
   `control_plane_root`.
4. **Fail**: "Cannot locate control-plane root. Provide
   control_plane_root explicitly, export CONTROL_PLANE_ROOT, or run
   sync-workspace.sh to stamp the workspace."

After resolution, verify that
`{control_plane_root}/agent-os/scripts/bootstrap-repo.sh` exists.
If it does not, fail — the control plane checkout may be stale or
missing.

### Shared tooling (from `control_plane_root`)

- `{control_plane_root}/agent-os/scripts/bootstrap-repo.sh`
- `{control_plane_root}/agent-os/scripts/validate-plan.py`
- `{control_plane_root}/agent-os/schemas/plan.schema.json`
- `{control_plane_root}/agent-os/templates/` (all template files)

## Required Inputs

| Input                  | Type   | Default       | Description                                      |
|------------------------|--------|---------------|--------------------------------------------------|
| `target_path`          | string | (required)    | Absolute or relative path to the target repo     |
| `owner`                | string | `$USER`       | Owner name for template rendering                |
| `ref`                  | string | (auto)        | Control plane branch/SHA for template rendering  |
| `control_plane_root`   | string | (resolved)    | Root of the Level-0 control-plane checkout       |
| `dry_run`              | bool   | `false`       | If true, run bootstrap in dry-run mode           |
| `init_git`             | bool   | `false`       | If true, run `git init` when target is not a git repo |
| `trust_codex_project`  | bool   | `false`       | If true, add the target path to host-local Codex trust config |

## Procedure

Execute these steps in order. Stop and report on the first blocking
failure unless all issues can be enumerated without side effects (in
which case, collect all failures before stopping).

### Step 0 — Resolve control plane root

1. Resolve `control_plane_root` using the resolution order above.
2. Verify `{control_plane_root}/agent-os/scripts/bootstrap-repo.sh`
   exists.
3. Verify `{control_plane_root}/agent-os/templates/` exists and contains
   the expected template files. The authoritative list of templates is
   the set of `render_template` calls in `bootstrap-repo.sh` itself —
   read that file to determine the current set rather than relying on a
   hardcoded list.
4. Verify `{control_plane_root}/agent-os/scripts/validate-plan.py` and
   `{control_plane_root}/agent-os/schemas/plan.schema.json` exist.
5. Record `control_plane_root` in the report header.

This step must succeed before any other step runs. If the control plane
cannot be located or is incomplete, nothing else is meaningful.

### Step 1 — Pre-flight: validate target path

1. Check whether `target_path` exists as a directory.
   - If it does not exist and `init_git` is `false`: fail with
     "Target path does not exist: <path>. Set init_git to create it."
   - If it does not exist and `init_git` is `true`: create the directory
     and run `git init` inside it.
2. Check whether `target_path` is a git repository (contains `.git`
   directory or is inside one).
   - If it is not a git repo and `init_git` is `false`: fail with
     "Target is not a git repository: <path>. Set init_git to
     initialize it."
   - If it is not a git repo and `init_git` is `true`: run `git init`
     inside it.
3. Record the resolved absolute path of `target_path` as `repo_root`.

### Step 2 — Pre-flight: check for existing bootstrap

1. Check whether `{repo_root}/AGENTS.md` already exists.
   - If it exists: report "Target appears to be already bootstrapped.
     AGENTS.md exists at <path>. The bootstrap script will skip
     existing files." This is a warning, not a blocking failure.
     Record which of the expected files already exist.
2. Record the pre-flight results in the report.

### Step 3 — Execute bootstrap

1. Assemble the bootstrap command:
   ```bash
   bash {control_plane_root}/agent-os/scripts/bootstrap-repo.sh \
     [--dry-run] \
     [--owner <owner>] \
     [--ref <ref>] \
     [--trust-codex-project] \
     {repo_root}
   ```
   - Include `--dry-run` if `dry_run` is `true`.
   - Include `--owner <owner>` if `owner` is provided and not empty.
   - Include `--ref <ref>` if `ref` is provided and not empty.
   - Include `--trust-codex-project` only if `trust_codex_project` is `true`.

2. Run the command and capture stdout, stderr, and exit code.

3. Parse the output to determine which files were created (`OK:`),
   skipped (`SKIP:`), or would be created in dry-run mode (`DRY-RUN:`).

4. If the exit code is non-zero, fail with the stderr output. Record
   the failure in the report and stop.

5. Record the bootstrap outcome in the report.

### Step 4 — Post-bootstrap: verify file existence

If `dry_run` is `true`, skip this step (report all verifications as
"skipped").

For each rendered file listed in the target repo data table above,
verify it exists at its expected path under `repo_root`. Record which
files are present and which are missing. If any expected file is missing
and was not reported as skipped (pre-existing), flag it as a
verification failure.

### Step 5 — Post-bootstrap: validate the canonical plan entrypoint

If `dry_run` is `true`, skip this step.

1. Verify `{repo_root}/plan/PLAN-index.yaml` exists.
2. Run PLAN validation:
   ```bash
   python {control_plane_root}/agent-os/scripts/validate-plan.py \
     {repo_root}/plan/PLAN-index.yaml \
     --schema {control_plane_root}/agent-os/schemas/plan.schema.json
   ```
3. Record the exit code and any error output. A non-zero exit is a
   verification failure.

The bootstrap script already runs this validation internally, but this
step provides an independent verification and captures the result in the
structured report.

### Step 6 — Post-bootstrap: verify local hooks

If `dry_run` is `true`, skip this step.

1. Verify `{repo_root}/.githooks/commit-msg` exists.
2. Verify `{repo_root}/.githooks/pre-push` exists.
3. Verify both hooks have the executable permission bit set.
   ```bash
   test -x {repo_root}/.githooks/commit-msg
   test -x {repo_root}/.githooks/pre-push
   ```
4. If either hook exists but is not executable, flag as a verification
   failure naming the specific hook.

### Step 7 — Post-bootstrap: verify directory structure

If `dry_run` is `true`, skip this step.

Verify the expected directory structure was created:

1. `{repo_root}/docs/adr/` directory exists.
2. `{repo_root}/.githooks/` directory exists.
3. `{repo_root}/.github/` directory exists.
4. `{repo_root}/.cursor/rules/` directory exists.
5. `{repo_root}/.kilo/rules/` directory exists.

Record completeness in the report.

### Step 8 — Assemble report and next-steps

1. Combine all results into the structured report format defined in
   Expected Outputs.

2. Determine the overall verdict:
   - **pass**: all pre-flight checks passed, bootstrap completed
     successfully (or dry-run completed), all post-bootstrap
     verifications passed.
   - **fail**: bootstrap script returned non-zero, or post-bootstrap
     verification found missing/invalid files.
   - **blocked**: pre-flight failed (target path invalid, control
     plane missing).

3. Include next-steps guidance (only for non-dry-run pass verdicts):
   - "Enable repo-local hooks with:
     `git -C <repo_root> config core.hooksPath .githooks`"
   - "Set up workspace resolution:
     `export CONTROL_PLANE_ROOT=<control_plane_root>`"
   - "Or run sync-workspace.sh to stamp the workspace."
   - "Review and customize plan/PLAN-index.yaml and plan/PLAN-current.yaml for project-specific milestones."
  - "Shared assets resolve from CONTROL_PLANE_ROOT in workspace mode.
     Optional vendoring is explicit via materialize-shared-asset.sh."
   - "Codex trust is host-local. Use --trust-codex-project only when the operator wants this target added to $CODEX_HOME/config.toml or ~/.codex/config.toml."

## Common-Case Command Sequence

For bootstrapping a new Layer-2 repo from a workspace where the control
plane lives alongside it:

```bash
# Variables (resolve once)
CP="/path/to/AgentOrchestrator"       # control_plane_root
TARGET="/path/to/NewProject"          # repo_root

# 1. Optional: create and init the target
mkdir -p "$TARGET" && git -C "$TARGET" init

# 2. Run bootstrap (shared tooling → target repo)
bash "$CP/agent-os/scripts/bootstrap-repo.sh" \
  --owner "MyName" \
  --ref "$(git -C "$CP" rev-parse --short HEAD)" \
  "$TARGET"

# 3. Verify the canonical plan entrypoint (shared tooling, repo data)
python "$CP/agent-os/scripts/validate-plan.py" \
  "$TARGET/plan/PLAN-index.yaml" \
  --schema "$CP/agent-os/schemas/plan.schema.json"

# 4. Verify both local hooks are executable
test -x "$TARGET/.githooks/commit-msg"
test -x "$TARGET/.githooks/pre-push"

# 5. Enable repo-local hooks
git -C "$TARGET" config core.hooksPath .githooks

# 6. Set workspace resolution
export CONTROL_PLANE_ROOT="$CP"
```

## Constraints

- **Procedural only**: this skill wraps existing bootstrap tooling. It
  must not define, redefine, or silently alter any governance rule. The
  templates and script are the canonical authority for what gets
  rendered.
- **Two-root integrity**: the bootstrap script and templates come from
  `control_plane_root`. Rendered files go to `repo_root`. Never confuse
  which root a file belongs to.
- **No modification of control plane**: this skill never writes to
  `control_plane_root`. All writes go to `repo_root`.
- **Skip, do not overwrite**: `bootstrap-repo.sh` skips files that
  already exist. This skill must not force-overwrite existing files.
- **Dry-run is available**: the default is to execute (not dry-run),
  since the bootstrap is a forward-only operation on a new repo.
  However, dry-run is available for preview.
- **No auto-commit**: the skill renders files but does not stage or
  commit them. The operator (or a separate skill invocation) handles
  the initial commit.
- **No push**: the skill operates locally. It does not push to any
  remote.

## Failure Handling

| Failure                                    | Behavior                                                  |
|--------------------------------------------|-----------------------------------------------------------|
| Control plane root not resolvable          | Fail with resolution instructions                         |
| bootstrap-repo.sh not found               | Fail with "bootstrap-repo.sh not found at <path>"         |
| Templates directory incomplete             | Fail with list of missing template files                   |
| validate-plan.py or schema not found       | Warn; skip post-bootstrap plan validation                 |
| Target path does not exist (init_git=false)| Fail with "Target path does not exist"                    |
| Target is not a git repo (init_git=false)  | Fail with "Target is not a git repository"                |
| Target already bootstrapped                | Warn; continue (script will skip existing files)          |
| bootstrap-repo.sh non-zero exit            | Fail with stderr output                                   |
| Expected files missing after bootstrap     | Fail with list of missing files                           |
| Plan validation fails post-bootstrap       | Fail with validation error details                        |
| Local hook not executable                  | Fail with the specific hook path that is not executable   |
| Directory structure incomplete             | Fail with list of missing directories                     |
| Python not available for validation        | Warn; skip PLAN validation, note in report                |

## Adapter Notes

### Claude

When invoked via Claude Code or Claude-based agents, this skill uses
`Bash` to run `bootstrap-repo.sh` and validation commands, `Read` to
verify file existence and content, and `Glob` to check directory
structure. For control plane resolution, check the environment for
`CONTROL_PLANE_ROOT`, or read the workspace `AGENTS.md` in the parent
of `repo_root` and extract the `Control plane:` line. The bootstrap
report is returned as direct text output.

### Codex

When invoked via Codex agents, use the file system and shell tools
available in the sandbox. Both `repo_root` and `control_plane_root`
must be accessible within the sandbox filesystem. If the workspace
layout places them as siblings, both should be mounted. The same
command sequences apply.

### Gemini

When invoked via Gemini CLI or Gemini-based agents, the skill is
referenced from `GEMINI.md` (the thin repo-local entrypoint). Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. The same shared validation tooling
and bootstrap procedure apply.

### Cursor

When invoked via Cursor, the skill is referenced from
`.cursor/rules/governance.mdc` (the thin repo-local entrypoint). Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. The same shared validation tooling
and bootstrap procedure apply.

### Kilo

When invoked via Kilo, the skill is referenced from
`.kilo/rules/governance.md` in bootstrapped repositories. Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. Run the same shared validation tooling
from `control_plane_root` against the target repo.

### Copilot

When invoked via GitHub Copilot agents, the skill is referenced from
`.github/copilot-instructions.md` (the thin repo-local entrypoint).
Control plane resolution uses the workspace layout or explicit
configuration. The same bootstrap procedure applies.
