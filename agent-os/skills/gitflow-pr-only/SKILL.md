# gitflow-pr-only

## Purpose

Provide repeatable, execution-layer procedures for the five core
operations of the PR-only Git Flow workflow. This skill does not define
governance rules. It applies the rules already defined in the canonical
authority `agent-os/workflow/git-flow-policy.md`, translating them into
concrete step-by-step procedures that any supported agent runtime can
execute.

This skill runs at any layer governed by the control plane:

- **Layer 0**: the control-plane repo itself.
- **Layer 2**: any bootstrapped repo — the skill reads governance from
  the Layer-0 checkout and operates on the target repo.

This skill is procedural. All normative rules it enforces are defined in
canonical authorities. When a rule must be verified, read the relevant
file — do not invent or restate governance rules from memory.

Canonical authorities (paths relative to `control_plane_root`):

- `agent-os/workflow/git-flow-policy.md` — branch model, invariants,
  forbidden operations, synchronization, PR topology, tagging, conflict
  resolution, branch protection
- `agent-os/workflow/shared-workflow.md` — three-layer model, automation
  phases
- `agent-os/workflow/git-automation-policy.md` — phase gates (A/B/C/D)
- `AGENTS.md` — commit message contract (also present locally at Layer 2)

Design reference (non-authoritative, for background and command rationale):

- `docs/design/gitflow-pr-only-terminal-workflow.md`

## Two-Root Model

This skill operates with two distinct roots. Every path used in the
procedures belongs to exactly one of them.

| Root                  | What lives there                                        |
|-----------------------|---------------------------------------------------------|
| `repo_root`           | The target repository: source code, tests, `plan/PLAN-index.yaml`,|
|                       | `AGENTS.md` (local copy), `.git` directory              |
| `control_plane_root`  | The Level-0 checkout: governance files, skill           |
|                       | definitions, shared scripts, schemas                    |

At Layer 0, both roots point to the same directory.
At Layer 2, they are different directories (typically siblings under a
workspace parent).

### Resolving `control_plane_root`

Use the first match:

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Workspace-first discovery**: use `CONTROL_PLANE_ROOT` if it is
   available as an environment variable or stamped into the workspace
   runtime files generated by `sync-workspace.sh`.
3. **Local detection**: if `agent-os/workflow/git-flow-policy.md` exists
   relative to `repo_root`, the target repo is itself the control plane.
   Set `control_plane_root = repo_root`.
4. **Fail**: "Cannot locate control-plane root. Provide
   control_plane_root explicitly, export CONTROL_PLANE_ROOT, or run
   sync-workspace.sh to stamp the workspace."

After resolution, verify that
`{control_plane_root}/agent-os/workflow/git-flow-policy.md` exists.
If it does not, fail — the control plane checkout may be stale or missing.

## Actions

This skill exposes five actions. Each action is a self-contained procedure.
The caller specifies the action and its required inputs.

| Action        | When to use                                              |
|---------------|----------------------------------------------------------|
| `start`       | Create a new topic branch and open a draft PR            |
| `sync`        | Synchronize a topic branch with its base before merge    |
| `merge`       | Merge a PR (single-PR or PR1 of a two-PR flow)          |
| `tag`         | Create an annotated tag after PR1 merge (hotfix/release) |
| `back-merge`  | Open and merge PR2 toward the back-merge target          |

## Required Inputs

### Common inputs (all actions)

| Input                  | Type   | Default       | Description                                     |
|------------------------|--------|---------------|-------------------------------------------------|
| `action`               | string | (required)    | One of: `start`, `sync`, `merge`, `tag`, `back-merge` |
| `repo_root`            | string | `.`           | Root of the target repository                   |
| `control_plane_root`   | string | (resolved)    | Root of the Level-0 control-plane checkout      |

### Action-specific inputs

#### `start`

| Input          | Type   | Default       | Description                                     |
|----------------|--------|---------------|-------------------------------------------------|
| `branch_type`  | string | (required)    | One of: `feature`, `bugfix`, `hotfix`, `release`, `support` |
| `name`         | string | (required)    | Branch name (e.g., `ABC-123-login`, `1.4.1`, `3.2.x`) |
| `base`         | string | (see below)   | Base branch override (required for `support`)   |

Default base branches (per git-flow-policy.md):
- `feature`, `bugfix`, `release`: `develop`
- `hotfix`: `main`
- `support`: no default — `base` is required

#### `sync`

| Input          | Type   | Default       | Description                                     |
|----------------|--------|---------------|-------------------------------------------------|
| `branch`       | string | (required)    | Full topic branch name (e.g., `feature/ABC-123`) |
| `base`         | string | (inferred)    | Base branch to sync from — inferred from branch family if not provided |

#### `merge`

| Input          | Type   | Default       | Description                                     |
|----------------|--------|---------------|-------------------------------------------------|
| `branch`       | string | (required)    | Full topic branch name                          |
| `target`       | string | (inferred)    | PR target branch — inferred from branch family  |

#### `tag`

| Input          | Type   | Default       | Description                                     |
|----------------|--------|---------------|-------------------------------------------------|
| `version`      | string | (required)    | Version string for the annotated tag (e.g., `1.4.1`) |
| `type`         | string | (required)    | One of: `hotfix`, `release` (for the tag message) |

#### `back-merge`

| Input          | Type   | Default       | Description                                     |
|----------------|--------|---------------|-------------------------------------------------|
| `branch`       | string | (required)    | Full topic branch name (hotfix or release)      |
| `target`       | string | (resolved)    | Back-merge target — resolved per policy         |

## Expected Outputs

A concise action report describing the executed or pending workflow step:

- `action` performed
- resolved `repo_root` and `control_plane_root`
- affected branch, base, target, or tag as applicable
- whether remote operations were completed or deferred because of
  sandbox/phase restrictions
- any conflicts, escalations, or pending human actions
- resulting PR URL, branch name, or tag reference when one is available

## Reusable Sub-Procedure — Workflow Content Cleanliness

Run this sub-procedure before any step that pushes commits, opens or updates a
PR, posts a PR comment/review, or merges a PR.

1. Read `{repo_root}/AGENTS.md` and
   `{control_plane_root}/agent-os/workflow/git-flow-policy.md`.
2. Inspect the commit messages that are about to leave the local repository in
   the pending push range. If there is no remote range yet, inspect the local
   commits that will seed the PR.
3. Inspect any PR title/body text and any PR comment/review text the action is
   about to submit.
4. If any inspected text contains AI/codegen attribution markers (for example
   `Co-Authored-By:`, `Co-authored-by:`, `Generated by`, or `Generated with`
   tied to an AI model, vendor, or code-generation tool), stop and clean the
   text before continuing.
5. Legitimate human co-author trailers are allowed and must not be removed by
   this check.

## Procedures

### Action: `start`

Create a new topic branch, push it, and open a draft PR.

**Pre-conditions**: the agent is at Phase B minimum (push + PR creation
are allowed per `git-automation-policy.md`). If Phase B is not unlocked,
perform only the local steps (branch creation) and report the pending
push and PR to the human.

**Steps**:

1. **Resolve roots** per the Two-Root Model section above.

2. **Determine the base branch**.
   - If `base` is provided, use it.
   - Otherwise, use the default for the branch family (see table above).
   - For `support`, fail if `base` is not provided: "support branches
     require an explicit base."

3. **Fast-forward the base branch from origin**.
   ```bash
   git checkout <base>
   git pull --ff-only origin <base>
   ```

4. **Create the topic branch**.
   - If git-flow AVH is installed and the branch type is `feature`,
     `bugfix`, `hotfix`, or `release`:
     ```bash
     git flow <branch_type> start <name>
     ```
   - If AVH is not installed, or the branch type is `support`:
     ```bash
     # For support:
     git flow support start <name> <base>
     # Or without AVH:
     git checkout -b <family>/<name>
     ```
   - The resulting branch name follows the pattern `<family>/<name>`
     (e.g., `feature/ABC-123-login`, `hotfix/1.4.1`, `support/3.2.x`).

5. **Run the workflow content cleanliness check** for any local commit
   messages and the draft PR text that will be created next.

6. **Push the branch immediately** (Workflow Invariant 1).
   ```bash
   git push -u origin <family>/<name>
   ```

7. **Open a draft PR immediately** (Workflow Invariant 2).
   - Determine the PR target:
     - `feature`, `bugfix`: `develop`
     - `hotfix`, `release`: `main`
     - `support`: no PR for the support line itself (it is long-lived).
       If this is a child branch of a support line, the target is the
       `support/*` parent.
   ```bash
   gh pr create \
     --base <target> \
     --head <family>/<name> \
     --draft \
     --fill
   ```
   - If the runtime cannot create PRs (sandbox restriction), report the
     pending PR to the human: "Draft PR needed: `<family>/<name>` toward
     `<target>`."

8. **Report** the created branch and draft PR URL (or pending PR notice).

**Support line special case**: when `branch_type` is `support`, the
`start` action creates the long-lived support line only. Actual work
happens on child branches created with a subsequent `start` call using
`branch_type: feature` or `bugfix` with `base: support/<name>`, or
by manually creating a child branch:
```bash
git checkout support/3.2.x
git pull --ff-only origin support/3.2.x
git checkout -b fix/3.2.x-BUG-789
git push -u origin fix/3.2.x-BUG-789
gh pr create --base support/3.2.x --head fix/3.2.x-BUG-789 --draft --fill
```

### Action: `sync`

Synchronize a topic branch with its base before a PR merge. This
implements the Synchronization Rule from `git-flow-policy.md`.

**Steps**:

1. **Resolve roots** per the Two-Root Model section above.

2. **Determine the base branch**.
   - If `base` is provided, use it.
   - Otherwise, infer from the branch family:
     - `feature/*`, `bugfix/*`: `develop`
     - `hotfix/*`: `main`
     - `release/*`: `develop` (for pre-PR1 sync; `main` is the PR1
       target, but the branch was born from `develop`)
     - Child branches of `support/*`: the `support/*` parent

3. **Fast-forward the local base branch from origin**.
   ```bash
   git checkout <base>
   git pull --ff-only origin <base>
   ```

4. **Switch to the topic branch**.
   ```bash
   git checkout <branch>
   ```

5. **Merge the base branch into the topic branch**.
   ```bash
   git merge <base>
   ```

6. **Handle conflicts** per the conflict resolution model in
   `git-flow-policy.md`:
   - **No conflicts**: proceed to push.
   - **Trivial conflicts** (only one side has semantic changes, or
     conflicts in generated files): resolve them, commit the merge, and
     document the resolution in the PR description or as a PR comment.
   - **Non-trivial conflicts** (both sides modified the same logical
     block, governance/authority files, or the agent is not confident):
     abort the merge (`git merge --abort`), report the conflicting files
     and hunks to the human, and wait for human resolution.

7. **Run the workflow content cleanliness check** for the outgoing commit
   range and for any PR comment/description text needed to document a trivial
   conflict resolution.

8. **Push the topic branch**.
   ```bash
   git push
   ```

9. **Report** the synchronization result (clean merge, trivial
   resolution with details, or escalation with conflict details).

### Action: `merge`

Merge a PR using the merge-commit strategy. This covers single-PR flows
(feature, bugfix, support child) and PR1 of two-PR flows (hotfix,
release).

**Pre-conditions**: Phase C authorization is required for PR merge per
`git-automation-policy.md`. If Phase C is not unlocked, report the
ready-to-merge state to the human and stop.

**Steps**:

1. **Resolve roots** per the Two-Root Model section above.

2. **Archive a closed milestone before merge** when the repo uses the
   split-plan layout.
   - If `{repo_root}/plan/PLAN-index.yaml` exists and the branch name
     embeds an `XNN` milestone ID, run:
     ```bash
     python {control_plane_root}/agent-os/scripts/archive-plan.py \
       --plan {repo_root}/plan/PLAN-index.yaml \
       --milestone <XNN> \
       --md {repo_root}/PLAN.md \
       --dot {repo_root}/PLAN.dot
     ```
   - Only do this when the milestone is already done in the current
     fragment. If archival fails, stop and report the blocking reason.

3. **Ensure the topic branch is synchronized** with its base. If the
   base has moved since the last sync, run the `sync` action first.

4. **Run the workflow content cleanliness check** for the outgoing commit
   range and the PR title/body or review/comment text that may be submitted in
   this action.

5. **Mark the PR as ready** (if it is still a draft).
   ```bash
   gh pr ready
   ```

6. **Wait for CI checks** (if applicable).
   ```bash
   gh pr checks --watch
   ```

7. **Merge the PR with a merge commit** (Workflow Invariant 7).
   ```bash
   gh pr merge --merge
   ```
   - Do NOT use `--delete-branch` (Forbidden Operation).
   - Do NOT use `--squash` or `--rebase` (Forbidden Operation).

8. **Fast-forward the local target branch from origin** (Workflow
   Invariant 9).
   - Determine the target:
     - `feature/*`, `bugfix/*`: `develop`
     - `hotfix/*`, `release/*` (PR1): `main`
     - Support child branches: the `support/*` parent
   ```bash
   git checkout <target>
   git pull --ff-only origin <target>
   ```

9. **Report** the merge result and the updated target branch.

**For two-PR flows** (hotfix, release): after this action completes
PR1, proceed to the `tag` action, then the `back-merge` action.

### Action: `tag`

Create an annotated tag on `main` after PR1 of a hotfix or release flow.

**Pre-conditions**: PR1 toward `main` has already been merged. The local
`main` is fast-forwarded from origin (done by the `merge` action).

**Steps**:

1. **Resolve roots** per the Two-Root Model section above.

2. **Ensure local `main` is up to date**.
   ```bash
   git checkout main
   git pull --ff-only origin main
   ```

3. **Create the annotated tag** (Tagging Policy from
   `git-flow-policy.md`).
   ```bash
   git tag -a <version> -m "<Type> <version>"
   ```
   - `<Type>` is `Hotfix` or `Release` based on the `type` input.
   - Example: `git tag -a 1.4.1 -m "Hotfix 1.4.1"`

4. **Push the tag to origin**.
   ```bash
   git push origin <version>
   ```

5. **Report** the created tag and its commit SHA.

### Action: `back-merge`

Open and merge PR2 from the same topic branch toward the back-merge
target. This completes two-PR flows (hotfix, release).

**Steps**:

1. **Resolve roots** per the Two-Root Model section above.

2. **Determine the back-merge target** (per PR Topology / Back-merge
   target selection in `git-flow-policy.md`):
   - If `target` is provided, use it.
   - Otherwise, check whether a `release/*` branch currently exists:
     - If yes: the back-merge targets that release branch.
     - If no: the back-merge targets `develop`.
   - To detect an active release branch:
     ```bash
     git branch -r --list 'origin/release/*'
     ```
     If any remote release branch exists, use it as the target.

3. **Run the workflow content cleanliness check** for the outgoing commit
   range and the PR title/body text that PR2 will use.

4. **Open PR2** from the topic branch toward the resolved target.
   ```bash
   gh pr create \
     --base <target> \
     --head <branch> \
     --fill
   ```
   - If the runtime cannot create PRs, report the pending PR to the
     human.

5. **Synchronize the topic branch with the back-merge target** using the
   same synchronization rule as the `sync` action:
   ```bash
   git checkout <target>
   git pull --ff-only origin <target>
   git checkout <branch>
   git merge <target>
   ```
   - Handle conflicts per the same classification model (trivial: agent
     resolves and documents; non-trivial: escalate to human).

6. **Run the workflow content cleanliness check** for the outgoing commit
   range and any PR comment/description text needed to document conflict
   resolution.

7. **Push the topic branch** after synchronization.
   ```bash
   git push
   ```

8. **Wait for CI checks** (if applicable).
   ```bash
   gh pr checks --watch
   ```

9. **Merge PR2 with a merge commit** (requires Phase C authorization).
   ```bash
   gh pr merge --merge
   ```
   - Do NOT use `--delete-branch`.

10. **Fast-forward the local back-merge target from origin**.
   ```bash
   git checkout <target>
   git pull --ff-only origin <target>
   ```

11. **Report** the back-merge result and the updated target branch.

## Quick-Reference: End-to-End Flows

These show the typical action sequence for each branch family. Each
action is a separate invocation of this skill.

### Feature / Bugfix (single-PR)

```
start  ->  [day-to-day work]  ->  sync  ->  merge
```

### Hotfix / Release (two-PR)

```
start  ->  [day-to-day work]  ->  sync  ->  merge (PR1)  ->  tag  ->  back-merge (PR2)
```

### Support (long-lived line + child branches)

```
start (support line)  ->  start (child branch)  ->  [work]  ->  sync  ->  merge
```

## Constraints

- **Procedural only**: this skill applies existing governance rules from
  `git-flow-policy.md`. It must not define, redefine, or silently alter
  any rule. When in doubt, read the canonical authority file.
- **Two-root integrity**: never read governance files from `repo_root`
  when they belong to `control_plane_root`, and vice versa.
- **No rebase** (Workflow Invariant 5): never rebase a topic branch.
  Always merge the base into the topic branch.
- **No branch deletion** (Workflow Invariant 8): agents never delete
  branches, local or remote.
- **Merge-commit only** (Workflow Invariant 7): PRs are merged with
  merge commits. No squash, no rebase merge.
- **Explicit staging only** (Workflow Invariant 4): stage files by name.
  Never use `git add -A` or `git add .`.
- **No direct push to protected branches**: never push directly to
  `main` or `develop`. All changes arrive via PR merge.
- **Phase gates**: respect automation phase restrictions. Branch creation
  and local commits are Phase A. Push and PR creation require Phase B.
  PR merge requires Phase C.
- **Immediate push and draft PR**: every new branch must be pushed and
  have a draft PR opened immediately after creation, regardless of
  expected branch lifetime.

## Failure Handling

| Failure                                  | Behavior                                                  |
|------------------------------------------|-----------------------------------------------------------|
| Control plane root not resolvable        | Fail with resolution instructions                         |
| Governance file missing at control plane | Fail with "git-flow-policy.md not found at `<path>`"      |
| `base` not provided for `support` start  | Fail with "support branches require an explicit base"      |
| Base branch ff-only pull fails           | Fail with "cannot fast-forward `<base>` — local divergence detected" |
| AVH not installed (start action)         | Fall back to `git checkout -b` with correct base           |
| Non-trivial merge conflict (sync)        | Abort merge, report conflicting files/hunks, wait for human |
| PR creation fails (sandbox restriction)  | Report pending PR details to human, continue local work    |
| Phase B not unlocked (push/PR)           | Perform local steps only, report pending push/PR           |
| Phase C not unlocked (merge)             | Report ready-to-merge state, stop                          |
| CI checks fail                           | Report failing checks, do not merge                        |
| PR merge conflict (target moved)         | Re-run `sync` action, then retry merge                     |
| Tag already exists                       | Fail with "tag `<version>` already exists"                 |
| No release branch found (back-merge)     | Default to `develop` as back-merge target                  |

## Adapter Notes

### Claude

When invoked via Claude Code or Claude-based agents, this skill uses
`Bash` to run git and gh commands from `repo_root`, `Read` to inspect
governance files from `control_plane_root`, and `Grep` to detect active
release branches. For control plane resolution, read the workspace
`AGENTS.md` in the parent of `repo_root` and extract the `Control
plane:` line, or check for `CONTROL_PLANE_ROOT` in the environment.
Draft PR creation uses `gh pr create` directly. Conflict resolution
output is returned as direct text to the operator.

### Codex

When invoked via Codex agents, use the file system and shell tools
available in the sandbox. Both `repo_root` and `control_plane_root`
must be accessible within the sandbox filesystem. Codex sandboxes may
restrict network access — if `git push` or `gh pr create` fail due to
sandbox restrictions, perform all local git operations (branch creation,
commits, merges) and report the pending remote operations (push, PR
creation, PR merge) to the human operator. The agent defers Phase B and
Phase C operations to the human or CI pipeline while still following the
governance rules.

### Kilo

Kilo uses `.kilo/rules/governance.md` as its thin repo-local
entrypoint in bootstrapped repositories. Kilo agents should resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. Command execution follows the same
shell sequences. Sandbox restrictions apply the same deferral model as
Codex.

### Copilot

When invoked via GitHub Copilot agents (Copilot Workspace or Copilot
Chat), the skill is referenced from `.github/copilot-instructions.md`
(the thin repo-local entrypoint). Copilot agents typically have access
to `gh` CLI for PR operations. Control plane resolution uses the
workspace layout or explicit configuration. The same procedures apply;
Copilot-specific behavior (e.g., inline suggestions vs. terminal
execution) is handled by the Copilot adapter profile.

### Gemini

When invoked via Gemini CLI or Gemini-based agents, the skill is
referenced from `GEMINI.md` (the thin repo-local entrypoint). Gemini
agents should resolve canonical governance from `AGENTS.md` and the
workflow authorities after the runtime entrypoint is loaded. The same
procedures apply; Gemini-specific instruction tuning belongs in the
profile or entrypoint layer, not in the shared skill.

### Cursor

When invoked via Cursor, the skill is referenced from
`.cursor/rules/governance.mdc` (the thin repo-local entrypoint). Cursor
agents should resolve canonical governance from `AGENTS.md` and the
workflow authorities after the runtime entrypoint is loaded. The same
procedures apply; Cursor-specific behavior belongs in the profile or
entrypoint layer, not in the shared skill.
