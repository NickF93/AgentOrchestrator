# quick-fix

## Purpose

Open a single F-type item and its owning `commit_group` in
`plan/PLAN-current.yaml` **before** any non-generated file is edited,
so low-effort fixes satisfy the tracking-first invariant from
`AGENTS.md` without the operator hand-crafting YAML.

The friction this addresses is real but narrow: even a one-character
typo fix requires a tracked plan item, a declared `commit_group`, a
scope, and an artifact list. Doing that by hand for every two-line
patch encourages either batching unrelated fixes into one item (which
the `commit_group` rule forbids) or quietly skipping the plan (which
the tracking-first rule forbids). `quick-fix` removes the friction
without relaxing either rule.

This skill is procedural: it applies rules already defined in canonical
authorities; it does not define, redefine, or relax any rule. When a
specific field, status, or check must be verified, read the relevant
authority under `control_plane_root` rather than restating it from
memory — authorities change, this file shouldn't have to.

## Two-Root Model

Every path used in the procedure belongs to exactly one root.

| Root                  | What lives there                                        |
|-----------------------|---------------------------------------------------------|
| `repo_root`           | The target repository: `plan/PLAN-index.yaml`,         |
|                       | `plan/PLAN-current.yaml`, `AGENTS.md` (local copy),    |
|                       | the in-scope file the fix touches, `.git`              |
| `control_plane_root`  | The Level-0 checkout: shared scripts, schemas,          |
|                       | canonical workflow files, skill definitions             |

At Layer 0 (the control-plane repo itself) both roots point to the
same directory. At Layer 2 (a bootstrapped repo) they are different
directories, typically siblings under a workspace parent.

### Resolving `control_plane_root`

Use the first match:

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Workspace-first discovery**: `CONTROL_PLANE_ROOT` is set as an
   environment variable or stamped into the workspace runtime files
   generated by `sync-workspace.sh`.
3. **Local detection**: if `agent-os/scripts/validate-plan.py` exists
   under `repo_root`, the target repo is itself the control plane.
   Set `control_plane_root = repo_root`.
4. **Fail**: "Cannot locate control-plane root. Provide
   control_plane_root explicitly, export CONTROL_PLANE_ROOT, or run
   sync-workspace.sh to stamp the workspace."

After resolution, verify that
`{control_plane_root}/agent-os/scripts/validate-plan.py` and
`{control_plane_root}/agent-os/workflow/item-taxonomy.md` both exist.
If either is missing, the checkout is stale — fail rather than guess
at fields the taxonomy may have changed.

### Shared tooling (from `control_plane_root`)

- `{control_plane_root}/agent-os/scripts/validate-plan.py`
- `{control_plane_root}/agent-os/scripts/render-plan.py`
- `{control_plane_root}/agent-os/schemas/plan.schema.json`
- `{control_plane_root}/agent-os/workflow/item-taxonomy.md`
- `{control_plane_root}/agent-os/workflow/lifecycle.md`

### Target repo data (from `repo_root`)

- `{repo_root}/plan/PLAN-current.yaml` (the file the skill writes to)
- `{repo_root}/plan/PLAN-index.yaml` (entrypoint passed to
  `validate-plan.py`)
- `{repo_root}/plan/archive/*.yaml` (used for ID-collision checks)
- `{repo_root}/AGENTS.md` (commit message contract)
- the in-scope file the fix will edit (only inspected for cleanliness;
  not modified by the skill)

## Canonical Authorities Referenced

The skill consults — never duplicates — the following authorities:

- `AGENTS.md` — commit message contract, mandatory commit rule,
  tracking-first rule
- `agent-os/workflow/item-taxonomy.md` — required fields for F-type
  items, identifier grammar, action-coherence table
- `agent-os/workflow/lifecycle.md` — status transitions
- `agent-os/workflow/shared-workflow.md` — three-layer model

## When to Use

Trigger this skill when **all** of these hold:

- One or two files need to change (typo, one-line bug, missing import,
  wrong constant, stale comment).
- No open plan item already covers the same scope.
- The fix is small enough that splitting it across multiple
  `commit_group`s would be overkill.
- The operator is already on a topic branch (branch creation is
  `gitflow-pr-only`'s job — see Constraints).

For larger changes — multiple files, multiple concerns, a test added
alongside — prefer a normal M-type item authored by hand or a
multi-item sprint. `quick-fix` is intentionally narrow: it optimises
the easy case so the easy case stays disciplined.

## Required Inputs

| Input                  | Type   | Default       | Description                                      |
|------------------------|--------|---------------|--------------------------------------------------|
| `fix_summary`          | string | (required)    | One-line description of the fix, used for both the item title and the commit subject |
| `scope_path`           | string | (required)    | File or directory prefix matching the `scope` regex `^(\.|[A-Za-z0-9._/-]+)$` |
| `artifacts_out`        | list   | `[scope_path]`| Files the fix will modify; defaults to the scope path when it's a single file |
| `repo_root`            | string | `.`           | Root of the target repository                    |
| `control_plane_root`   | string | (resolved)    | Root of the Level-0 control-plane checkout       |
| `parent_sprint`        | string | (inferred)    | Sprint ID under which the F-item belongs; defaults to the most recent `in_progress` sprint in `PLAN-current.yaml`; if none, the skill escalates |
| `current_branch`       | string | (read via git)| Topic branch name; the skill refuses to scaffold while on `develop` or `main` |
| `commit_type`          | string | `fix`         | Commit-message type per the contract in `AGENTS.md`; usually `fix`, occasionally `chore` or `docs` |
| `commit_scope`         | string | (derived)     | Commit-message scope; derived from the deepest meaningful path component of `scope_path` when omitted |

## Expected Outputs

A structured report. The skill does not auto-commit; the operator
applies the fix and commits with the prepared message.

```
verdict: ready | blocked | fail
findings:
  - <finding or "none">
evidence:
  - repo_root: <path>
  - control_plane_root: <path>
  - current_branch: <branch>
  - parent_sprint: <SNN.M>
  - next_item_id: <F-item ID>
  - next_commit_group: <cgNNN>
proposed_item_yaml: |
  <YAML block ready to paste under `items:` in PLAN-current.yaml>
proposed_commit_group_yaml: |
  <YAML block ready to paste under `commit_groups:` in PLAN-current.yaml>
commands_run:
  - `python <cp>/agent-os/scripts/validate-plan.py <plan> --schema <cp>/agent-os/schemas/plan.schema.json` -> exit 0
proposed_commit_message: |
  <type>(<scope>): <description>

  Summary: ...
  Scope: <scope_path>
  Items: <F-item ID>
  Validation: validate-plan.py exits 0; render idempotent.

  Refs: <F-item ID>, <cgNNN>
next_steps:
  - Apply the edit in <scope_path>.
  - Advance <F-item ID> status: planned -> ready -> in_progress -> done.
  - Re-run validate-plan.py and render-plan.py.
  - git add <files> && git commit -m "<prepared message>"
```

## Procedure

Execute steps in order. Stop and report on the first blocking failure
unless several issues can be enumerated without side effects, in which
case collect them all before stopping — the operator should not have
to re-run the skill just to discover the next blocker.

### Step 0 — Resolve roots

1. Resolve `control_plane_root` using the resolution order above.
2. Verify `validate-plan.py` and `item-taxonomy.md` exist under it.
3. Resolve `repo_root` to an absolute path.
4. Record both roots in the report header.

### Step 1 — Verify topic branch

1. Read the current branch from `git -C {repo_root} rev-parse --abbrev-ref HEAD`.
2. If the branch is `develop`, `main`, or any other long-lived branch
   declared in `agent-os/workflow/git-flow-policy.md`, stop with:
   "Tracking-first applies on topic branches only. Use the
   `gitflow-pr-only` skill (`action: start`) to create a topic branch
   (e.g. `bugfix/<name>` or `feature/<name>`), then re-run quick-fix."
3. Record the topic branch in the report.

### Step 2 — Verify clean working tree for the scope

1. Run `git -C {repo_root} status --porcelain -- {scope_path}`.
2. If the output is non-empty (the in-scope file is already dirty),
   stop with: "Refusing to scaffold tracking after an edit — stash or
   revert the in-scope change first, then re-run quick-fix."

This enforces the ordering: plan first, then edit. Retroactive
tracking defeats the audit value of the plan, because anyone reviewing
the commit later cannot tell whether the F-item really existed before
the change or was backfilled to look like it did.

### Step 3 — Determine the parent sprint

1. Parse `{repo_root}/plan/PLAN-current.yaml`.
2. If `parent_sprint` was provided, verify it exists and its `status`
   is `planned`, `ready`, or `in_progress`. Reject closed/archived
   sprints.
3. If `parent_sprint` was not provided, pick the most recently declared
   sprint with `status: in_progress` whose milestone is also active.
4. If no suitable sprint exists, stop with: "No open sprint to attach
   an F-item to. Open a sprint first (orchestrator role) — quick-fix
   does not auto-create sprints because sprint boundaries are a
   planning decision, not a fix-time decision."

### Step 4 — Allocate identifiers

The skill reads — it never invents — identifiers. Compute both IDs by
scanning the active plan and the archive index.

1. From the sprint ID (e.g. `S45.2`), item IDs follow
   `<TYPE><milestone>.<sprint>.<sequence>` per `item-taxonomy.md`.
2. `next_item_id` is the next free `F<milestone>.<sprint>.<n>` under
   that sprint, taking active *and* archived items into account.
3. `next_commit_group` is `cg<n+1>` where `<n>` is the highest
   `commit_group` integer across `PLAN-current.yaml` and every
   archived fragment.
4. Refuse to reuse any ID that ever appeared in the archive — that
   would silently break historical-lookup invariants.

### Step 5 — Compose the F-item and commit_group blocks

Compose the F-item with the minimum required fields from
`item-taxonomy.md` (`id`, `type`, `title`, `status`, `role`, `effort`,
`actions`, `parent`, `commit_group`) plus the fix-relevant
`scope` and `artifacts_out`.

`proposed_item_yaml`:

```yaml
- id: <next_item_id>
  parent: <parent_sprint>
  type: F
  title: <fix_summary>
  actions:
    - implement
  status: planned
  role: implementer
  effort: low
  commit_group: <next_commit_group>
  scope: <scope_path>
  artifacts_out:
    - <each entry from artifacts_out, one per line>
```

`proposed_commit_group_yaml`:

```yaml
- id: <next_commit_group>
  title: <fix_summary>
  items:
    - <next_item_id>
  notes: 'Scaffolded via quick-fix skill. One F-item, one commit.'
```

Write both blocks into the appropriate sections of
`{repo_root}/plan/PLAN-current.yaml`. Preserve the YAML conventions
already in the file (two-space indent, trailing newline, quoted
multiline notes only where the parser needs them) so the diff stays
review-friendly.

### Step 6 — Validate

Run from `repo_root`, using shared tooling from `control_plane_root`:

```bash
python {control_plane_root}/agent-os/scripts/validate-plan.py \
  {repo_root}/plan/PLAN-index.yaml \
  --schema {control_plane_root}/agent-os/schemas/plan.schema.json
```

A non-zero exit is a blocking failure: revert the `PLAN-current.yaml`
write and report the validator output. Proceeding to the edit phase
with an invalid plan poisons the closure commit, which is harder to
unwind than a revert here.

Optionally re-render plan views so the operator can include them in
the final commit:

```bash
python {control_plane_root}/agent-os/scripts/render-plan.py \
  {repo_root}/plan/PLAN-index.yaml \
  --md {repo_root}/PLAN.md \
  --dot {repo_root}/PLAN.dot
```

### Step 7 — Assemble closure expectations

The skill does not commit. Hand the operator a complete next-steps
list:

1. Apply the actual fix to `<scope_path>`.
2. Advance the new F-item:
   `planned -> ready -> in_progress -> done` (or with `review` and
   `verified` between if the operator wants the explicit walk).
3. Re-run `validate-plan.py` and `render-plan.py` after the edit.
4. Stage exactly the files in `artifacts_out` plus
   `plan/PLAN-current.yaml`, `PLAN.md`, and `PLAN.dot`.
5. Commit with the prepared `proposed_commit_message` (one commit
   closes the single `commit_group`).
6. No push. Push is Phase B; merge is Phase C — both go through
   `gitflow-pr-only`.

For a one-shot F-item commit_group, the closure is direct: the F-item
moving to `done` and the single commit landing **is** the closure. A
separate C-type checkpoint item is unnecessary unless the operator
wants one for audit reasons; in that case, use
`plan-checkpoint-close`.

## Worked Example: Tiny Typo Fix

A concrete walk-through. The IDs `F99.1.1`, `cg999`, and `S99.1` are
intentionally far outside any plausible real milestone range so a
reader never confuses them with planned work.

**Scenario**: a one-character typo in
`agent-os/workflow/lifecycle.md` — the word `transitions` is
misspelled as `transtions` in the status-flow section.

### Inputs supplied to the skill

```
fix_summary: "correct typo in lifecycle status list"
scope_path: agent-os/workflow/lifecycle.md
artifacts_out: [agent-os/workflow/lifecycle.md]
parent_sprint: S99.1
commit_type: fix
commit_scope: workflow
```

### What the skill writes into `plan/PLAN-current.yaml`

Appended under `items:`:

```yaml
- id: F99.1.1
  parent: S99.1
  type: F
  title: correct typo in lifecycle status list
  actions:
    - implement
  status: planned
  role: implementer
  effort: low
  commit_group: cg999
  scope: agent-os/workflow/lifecycle.md
  artifacts_out:
    - agent-os/workflow/lifecycle.md
```

Appended under `commit_groups:`:

```yaml
- id: cg999
  title: correct typo in lifecycle status list
  items:
    - F99.1.1
  notes: 'Scaffolded via quick-fix skill. One F-item, one commit.'
```

### Validator run

```
$ python {control_plane_root}/agent-os/scripts/validate-plan.py \
    plan/PLAN-index.yaml \
    --schema {control_plane_root}/agent-os/schemas/plan.schema.json
OK: plan/PLAN-index.yaml is valid against agent-os/schemas/plan.schema.json
```

### Operator applies the fix and advances status

Edit `agent-os/workflow/lifecycle.md`: change `transtions` to
`transitions`. Then in `plan/PLAN-current.yaml` flip
`F99.1.1.status` from `planned` to `done` (passing through `ready`
and `in_progress` is optional).

### Operator commits the cg999 commit_group

```
$ python {control_plane_root}/agent-os/scripts/render-plan.py plan/PLAN-index.yaml \
  --md PLAN.md --dot PLAN.dot
$ git add agent-os/workflow/lifecycle.md plan/PLAN-current.yaml PLAN.md PLAN.dot
$ git commit -m "$(cat <<'EOF'
fix(workflow): correct typo in lifecycle status list

Summary: Fix a one-character typo in the status-flow section of
agent-os/workflow/lifecycle.md. No semantic change to the lifecycle
model; documentation correction only.

Scope: agent-os/workflow/lifecycle.md

Items: F99.1.1
Validation: validate-plan.py exits 0; render idempotent.

Refs: F99.1.1, cg999
EOF
)"
```

That single commit closes `cg999`, satisfies the
`<type>(<scope>): <description>` header rule, includes the
`Refs: <item IDs>, <commit_group ID>` footer required for tracked
work, and lands on the operator's topic branch. No push yet — push
goes through `gitflow-pr-only`.

## Common-Case Command Sequence

For a Layer-2 repo where the control plane lives alongside it in a
workspace:

```bash
# Variables (resolve once)
CP="/path/to/AgentOrchestrator"       # control_plane_root
REPO="/path/to/MyProject"             # repo_root

# 1. Verify topic branch (refuse on develop/main)
git -C "$REPO" rev-parse --abbrev-ref HEAD

# 2. Verify clean scope
git -C "$REPO" status --porcelain -- <scope_path>

# 3. (The skill writes the F-item + cg blocks into PLAN-current.yaml)

# 4. Validate the plan
python "$CP/agent-os/scripts/validate-plan.py" \
  "$REPO/plan/PLAN-index.yaml" \
  --schema "$CP/agent-os/schemas/plan.schema.json"

# 5. Render plan views
python "$CP/agent-os/scripts/render-plan.py" "$REPO/plan/PLAN-index.yaml" \
  --md "$REPO/PLAN.md" --dot "$REPO/PLAN.dot"

# 6. Operator applies the fix, advances F-item status,
#    then commits with the prepared message.
```

For Layer 0 (the control-plane repo fixing itself), replace both
`$CP` and `$REPO` with the same path.

## Constraints

- **Procedural only**: this skill applies existing governance rules.
  It does not define, redefine, or silently alter any rule. When in
  doubt, read the canonical authority file from `control_plane_root`.
- **Two-root integrity**: never read repo data from the control plane
  or run shared tooling from the wrong root.
- **Tracking-first hard gate**: write `plan/PLAN-current.yaml` and
  run `validate-plan.py` before the operator touches the in-scope
  file. If the in-scope file is already dirty, refuse and escalate —
  retroactive tracking is not tracking.
- **`commit_group` predeclaration**: the `commit_group` ID is
  allocated and written before any edit. It is never invented at
  commit time and never reshuffled afterward.
- **Single F-item per invocation**: one fix, one F-item, one
  `commit_group`, one commit. Batching unrelated fixes is forbidden —
  open separate invocations or use a normal multi-item sprint.
- **No branch creation**: refuse on `develop`/`main` and point to
  `gitflow-pr-only`. Branch creation is that skill's job.
- **No sprint auto-creation**: if no open sprint exists, escalate.
  Sprint boundaries are a planning decision.
- **No auto-commit**: the operator commits per the
  `<type>(<scope>): <description>` contract in `AGENTS.md`. The skill
  prepares the message text; it does not run `git commit`.
- **No push**: push is Phase B and goes through `gitflow-pr-only`
  (`sync` or `merge`).
- **No AI attribution in commit messages**: the prepared message must
  not include `Co-Authored-By:` or any line attributing authorship to
  a generative AI model or code-generation tool. Legitimate human
  co-author trailers remain allowed.

## Failure Handling

| Failure                                              | Behavior                                                                          |
|------------------------------------------------------|-----------------------------------------------------------------------------------|
| Control-plane root not resolvable                    | Fail with resolution instructions                                                 |
| `validate-plan.py` missing under control plane       | Fail with "validate-plan.py not found at `<path>`; control-plane checkout may be stale" |
| On `develop` / `main` / other long-lived branch      | Fail and point to `gitflow-pr-only` action `start`                                |
| In-scope file already dirty in the working tree      | Fail with "Refusing to scaffold tracking after an edit — stash or revert first"   |
| No open sprint in `PLAN-current.yaml`                | Fail with "No open sprint — open a sprint first; quick-fix does not auto-create sprints" |
| Parent sprint is closed or archived                  | Fail with the sprint ID and its current status                                    |
| `scope_path` violates the scope regex                | Fail with the regex and the offending value                                       |
| `artifacts_out` is empty                             | Fail with "F-item requires at least one declared artifact"                        |
| `next_item_id` collides with an existing ID          | Fail with the colliding ID and its location (active or archive)                   |
| `next_commit_group` collides with an archived cg     | Fail with the colliding cg ID                                                     |
| Scope collides with an existing open item            | Block; report the colliding item and reference `scope_exclusive` semantics if applicable |
| `validate-plan.py` exits non-zero after the write    | Revert the `PLAN-current.yaml` write and report stderr; the operator does not proceed to edit |
| Operator skipped tracking and made the edit anyway   | Detected at Step 2; fail and require revert before re-running                     |
| YAML parse error on `PLAN-current.yaml`              | Fail with parse error details                                                     |
| Plan-index missing or unreadable                     | Fail with "PLAN-index.yaml not found or unreadable"                               |

## Adapter Notes

### Claude

Use `Read` to parse `plan/PLAN-current.yaml`, `plan/PLAN-index.yaml`,
and the archive fragments listed in the index; `Bash` for
`git rev-parse --abbrev-ref HEAD`, `git status --porcelain`, and the
shared `validate-plan.py` / `render-plan.py` scripts; `Edit` (or
`Write`) to insert the proposed YAML blocks. Return the structured
report as direct text. For control-plane resolution, read the
workspace `AGENTS.md` in the parent of `repo_root` and extract the
`Control plane:` line.

### Codex

Use the file-system and shell tools available in the sandbox. Both
`repo_root` and `control_plane_root` must be reachable. The skill
performs no network operations — only local plan reads/writes and
shared-tooling invocation. Sandboxes that disallow `git status`
should fall back to reading the working tree directly, but the
in-scope-cleanliness check must still execute before any write.

procedure as Claude; Gemini-specific tuning belongs in the profile or
entrypoint layer, not in the shared skill.
