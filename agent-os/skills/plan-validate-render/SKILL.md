# plan-validate-render

## Purpose

Provide a repeatable, execution-layer procedure for validating the
canonical plan entrypoint and rendering its generated views. This skill wraps
two existing scripts — `validate-plan.py` and `render-plan.py` — with
structured reporting, warning/error classification, and render drift
detection. It does not define governance rules. It applies the
validation and rendering logic already implemented in canonical tooling
and reports the results using the `check-result-v1` protocol.

This skill runs at any layer governed by the control plane:

- **Layer 0**: the control-plane repo itself — tooling and data are both
  local.
- **Layer 2**: any bootstrapped repo — the skill reads data from the
  target repo and runs shared tooling from the Layer-0 checkout.

This skill is procedural. All normative rules it enforces are defined in
canonical authorities and implemented by the wrapped scripts. When a
specific rule must be verified, read the relevant file — do not invent
or restate governance rules from memory.

Canonical authorities (paths relative to `control_plane_root`):

- `agent-os/scripts/validate-plan.py` — plan validation (17 checks)
- `agent-os/scripts/render-plan.py` — plan view rendering
- `agent-os/schemas/plan.schema.json` — PLAN schema for validation
- `agent-os/workflow/lifecycle.md` — lifecycle states and transitions
- `agent-os/workflow/item-taxonomy.md` — item types and required fields

## Two-Root Model

This skill operates with two distinct roots. Every path used in the
procedure belongs to exactly one of them.

| Root                  | What lives there                                        |
|-----------------------|---------------------------------------------------------|
| `repo_root`           | The target repository: `plan/PLAN-index.yaml`, `PLAN.md`,         |
|                       | `PLAN.dot`, `REPO_MAP.md`, repo code and tests         |
| `control_plane_root`  | The Level-0 checkout: validation and render scripts,    |
|                       | schema, shared asset registry, skill definitions        |

At Layer 0, both roots point to the same directory.
At Layer 2, they are different directories (typically siblings under a
workspace parent).

### Resolving `control_plane_root`

Use the first match:

1. **Explicit input**: caller provides `control_plane_root` directly.
2. **Workspace-first discovery**: use `CONTROL_PLANE_ROOT` if it is
   available as an environment variable or stamped into the workspace
   runtime files generated by `sync-workspace.sh`.
3. **Local detection**: if `agent-os/scripts/validate-plan.py` exists
   relative to `repo_root`, the target repo is itself the control plane.
   Set `control_plane_root = repo_root`.
4. **Fail**: "Cannot locate control-plane root. Provide
   control_plane_root explicitly, export CONTROL_PLANE_ROOT, or run
   sync-workspace.sh to stamp the workspace."

After resolution, verify that
`{control_plane_root}/agent-os/scripts/validate-plan.py` exists.
If it does not, fail — the control plane checkout may be stale or
missing.

### Shared tooling (from `control_plane_root`)

- `{control_plane_root}/agent-os/scripts/validate-plan.py`
- `{control_plane_root}/agent-os/scripts/render-plan.py`
- `{control_plane_root}/agent-os/schemas/plan.schema.json`
- `{control_plane_root}/agent-os/registry/shared-assets.yaml`

### Target repo data (from `repo_root`)

- `{repo_root}/plan/PLAN-index.yaml` (or `plan_path` if overridden)
- `{repo_root}/PLAN.md` (generated view — may or may not exist yet)
- `{repo_root}/PLAN.dot` (generated view — may or may not exist yet)
- `{repo_root}/REPO_MAP.md` (optional — used by `--check-freshness`)

## Required Inputs

| Input                    | Type   | Default                                     | Description                                                    |
|--------------------------|--------|---------------------------------------------|----------------------------------------------------------------|
| `plan_path`              | string | `plan/PLAN-index.yaml`                      | Path to the canonical plan entrypoint (relative to `repo_root`) |
| `schema_path`            | string | `agent-os/schemas/plan.schema.json`         | Path to the JSON schema (relative to `control_plane_root`)     |
| `check_freshness`        | bool   | `false`                                     | If true, check REPO_MAP.md freshness at checkpoint boundaries  |
| `previous_plan`          | string | (none)                                      | Optional path to a previous plan entrypoint for lifecycle transition checks |
| `shared_asset_registry`  | string | (auto-resolved from `control_plane_root`)   | Path to shared asset registry YAML                             |
| `repo_root`              | string | `.`                                         | Root of the target repository                                  |
| `control_plane_root`     | string | (resolved)                                  | Root of the Level-0 control-plane checkout                     |
| `render`                 | bool   | `true`                                      | If true, render PLAN.md and PLAN.dot after validation          |
| `check_drift`            | bool   | `true`                                      | If true, check for render drift after rendering                |

## Expected Outputs

A structured report following the `check-result-v1` protocol:

```
verdict: pass | warn | fail | blocked
findings:
  errors:
    - <error finding or explicit none>
  warnings:
    - <warning finding or explicit none>
evidence:
  - repo_root: <path>
  - control_plane_root: <path>
  - plan_path: <resolved path>
  - schema_path: <resolved path>
  - validate_exit_code: <0|1|2>
  - render_exit_code: <0|2|skipped>
  - render_drift: <true|false|skipped>
commands_run:
  - `python <cp>/agent-os/scripts/validate-plan.py <plan> --schema <schema> [flags]` -> exit <code>
  - `python <cp>/agent-os/scripts/render-plan.py <plan>` -> exit <code>
  - `git diff PLAN.md PLAN.dot` -> <clean|dirty>
ready_to_close: true | false
follow_up:
  - <optional next action>
```

### Verdict Logic

| Condition | Verdict |
|-----------|---------|
| validate-plan.py exits 0, no render drift, no errors | **pass** |
| validate-plan.py exits 0, warnings only, render drift acceptable | **warn** |
| validate-plan.py exits 1 (validation failure) | **fail** |
| validate-plan.py exits 2 (system error), or scripts missing | **blocked** |
| render-plan.py exits non-zero | **fail** |
| Render drift detected and `check_drift` is true | **warn** (drift is flagged, not blocking by itself) |

## Procedure

Execute these steps in order. Stop and report on the first blocking
failure unless all issues can be enumerated without side effects (in
which case, collect all failures before stopping).

### Step 0 — Resolve roots

1. Resolve `control_plane_root` using the resolution order above.
2. Verify `{control_plane_root}/agent-os/scripts/validate-plan.py`
   exists.
3. Verify `{control_plane_root}/agent-os/scripts/render-plan.py`
   exists.
4. Verify `{control_plane_root}/{schema_path}` exists.
5. Resolve `plan_path` to an absolute path under `repo_root`.
6. Verify the plan file exists.
7. Record both roots in the report header.

This step must succeed before any other step runs. If the control plane
cannot be located or required files are missing, nothing else is
meaningful.

### Step 1 — Run validation

1. Assemble the validation command:
   ```bash
   python {control_plane_root}/agent-os/scripts/validate-plan.py \
     {repo_root}/{plan_path} \
     --schema {control_plane_root}/{schema_path} \
     [--check-freshness] \
     [--previous-plan {previous_plan}] \
     [--shared-asset-registry {shared_asset_registry}]
   ```
   - Include `--check-freshness` if `check_freshness` is `true`.
   - Include `--previous-plan` if `previous_plan` is provided.
   - Include `--shared-asset-registry` if `shared_asset_registry` is
     provided and differs from the auto-resolved default.

2. Run the command and capture stdout, stderr, and exit code.

3. Record the exit code and full output in the report.

### Step 2 — Interpret validation output

Parse the output from Step 1 to classify findings:

1. **Lines starting with `OK:`** — validation passed. Record the
   success message.

2. **Lines starting with `WARNING:`** — advisory findings that do not
   block. Classify into categories:
   - Type/action coherence warnings (e.g., "action 'X' is not in
     recommended set for type Y")
   - Scope collision warnings

3. **Lines starting with `ERROR:`** — hard failures. Classify into
   categories:
   - Schema validation errors
   - Identifier format violations
   - Dangling reference errors (depends_on, commit_group)
   - Dependency cycle detection
   - Commit group coherence violations
   - Dependency status violations
   - Phase-gate violations
   - Lifecycle transition violations
   - Shared asset reference violations
   - REPO_MAP freshness violations

4. **Exit code interpretation**:
   - Exit 0: all checks passed (warnings may be present)
   - Exit 1: one or more hard failures detected
   - Exit 2: system error (file not found, parse error, missing
     dependency)

5. Record all findings separated into `errors` and `warnings` arrays.

### Step 3 — Run rendering

If `render` is `false`, skip this step and record render as "skipped"
in the report.

1. Run the render command:
   ```bash
   python {control_plane_root}/agent-os/scripts/render-plan.py \
     {repo_root}/{plan_path} \
     --md {repo_root}/PLAN.md \
     --dot {repo_root}/PLAN.dot
   ```

2. Capture stdout, stderr, and exit code.

3. If the exit code is non-zero, record the failure. This is a blocking
   error — the generated views could not be produced.

4. Record the render outcome in the report.

### Step 4 — Detect render drift

If `check_drift` is `false`, or if rendering was skipped or failed, skip
this step and record drift check as "skipped" in the report.

1. Check whether `repo_root` is inside a git repository:
   ```bash
   git -C {repo_root} rev-parse --is-inside-work-tree
   ```
   If not inside a git repo, skip drift detection and record as
   "not a git repo — drift check skipped."

2. Run git diff on the generated files:
   ```bash
   git -C {repo_root} diff -- PLAN.md PLAN.dot
   ```

3. Interpret the result:
   - **Empty diff**: no drift. Generated files match the committed
     state. This is the expected outcome after a render following a
     plan update that was already committed.
   - **Non-empty diff**: drift detected. The generated files differ
     from the committed state. This typically means the plan was
     updated but the generated views were not re-rendered, or the
     render was just run and the new output has not yet been committed.

4. Record whether drift was detected and, if so, the summary of changed
   lines (e.g., "+N/-M in PLAN.md, +N/-M in PLAN.dot").

### Step 5 — Assemble report

1. Combine all results into the `check-result-v1` protocol format.

2. Determine the overall verdict using the verdict logic table above.

3. Set `ready_to_close`:
   - `true` if verdict is `pass` or `warn` with only advisory warnings.
   - `false` if verdict is `fail` or `blocked`.

4. If render drift was detected, add a follow-up entry:
   "Stage and commit PLAN.md and PLAN.dot to resolve render drift."

5. If validation warnings were present, add follow-up entries noting
   the advisory findings for human review.

## Constraints

- **Procedural only**: this skill wraps existing validation and
  rendering tooling. It does not define, redefine, or silently alter
  any governance rule. The scripts are the canonical authority for
  what gets validated and rendered.
- **Two-root integrity**: validation scripts and schema come from
  `control_plane_root`. Plan data and generated files live in
  `repo_root`. Never confuse which root a file belongs to.
- **No modification of the canonical plan entrypoint**: this skill reads and validates
  the plan. It does not modify plan content. Status transitions
  and item updates are outside this skill's scope.
- **Rendering overwrites generated files**: `render-plan.py` writes
  PLAN.md and PLAN.dot in place. This is expected behavior — these
  are generated artifacts, not authored files.
- **No auto-commit**: the skill renders files but does not stage or
  commit them. The operator (or a checkpoint closure skill) handles
  the commit.
- **Deterministic for same input**: running the skill twice on the
  same canonical plan entrypoint produces the same validation output and the same
  rendered files.
- **Scripts are authoritative**: when the skill's interpretation of
  a check conflicts with the script's actual behavior, the script
  wins. The skill's classification of warnings and errors is a
  convenience layer, not a normative override.

## Failure Handling

| Failure                                      | Behavior                                                  |
|----------------------------------------------|-----------------------------------------------------------|
| Control plane root not resolvable            | Fail with resolution instructions                         |
| validate-plan.py not found                   | Fail with "validate-plan.py not found at `<path>`"        |
| render-plan.py not found                     | Fail with "render-plan.py not found at `<path>`"          |
| Schema file not found                        | Fail with "plan.schema.json not found at `<path>`"        |
| Plan entrypoint not found                   | Fail with "Plan file not found: `<path>`"                 |
| validate-plan.py exits 1 (validation fail)   | Report all errors with categories; verdict **fail**       |
| validate-plan.py exits 2 (system error)      | Report system error details; verdict **blocked**          |
| render-plan.py exits non-zero                | Report render error; verdict **fail**                     |
| Python not available                         | Fail with "Python not available — cannot run tooling"     |
| Git not available (for drift check)          | Warn; skip drift detection; note in report                |
| Render drift detected                        | Warn; include drift summary; suggest commit               |
| REPO_MAP freshness violation                 | Report as error (hard-fail from validate-plan.py)         |
| Shared asset registry missing (auto-resolve) | Warn; skip registry validation; note in report            |

## Common-Case Command Sequence

For a Layer-2 repo where the control plane lives alongside it in a
workspace:

```bash
# Variables (resolve once)
CP="/path/to/AgentOrchestrator"       # control_plane_root
REPO="/path/to/MyProject"             # repo_root

# 1. Validate the plan (shared tooling, repo data)
python "$CP/agent-os/scripts/validate-plan.py" \
  "$REPO/plan/PLAN-index.yaml" \
  --schema "$CP/agent-os/schemas/plan.schema.json"

# 2. Freshness check (if applicable)
python "$CP/agent-os/scripts/validate-plan.py" \
  "$REPO/plan/PLAN-index.yaml" --check-freshness

# 3. Render plan views (shared tooling, repo data)
python "$CP/agent-os/scripts/render-plan.py" "$REPO/plan/PLAN-index.yaml" \
  --md "$REPO/PLAN.md" --dot "$REPO/PLAN.dot"

# 4. Check for render drift (in repo)
git -C "$REPO" diff -- PLAN.md PLAN.dot
```

For Layer 0 (control plane validating its own plan), replace both
`$CP` and `$REPO` with the same path.

## Adapter Notes

### Claude

When invoked via Claude Code or Claude-based agents, this skill uses
`Bash` to run validation and render scripts from `control_plane_root`
against the target repo's data, `Read` to inspect the canonical plan entrypoint or
validation output if needed, and `Grep` to locate REPO_MAP.md for
freshness checks. For control plane resolution, check the environment
for `CONTROL_PLANE_ROOT`, or read the workspace `AGENTS.md` in the
parent of `repo_root` and extract the `Control plane:` line, or detect
the local presence of `agent-os/scripts/validate-plan.py`. The
structured report is returned as direct text output.

### Codex

When invoked via Codex agents, use the file system and shell tools
available in the sandbox. Both `repo_root` and `control_plane_root`
must be accessible within the sandbox filesystem. If the workspace
layout places them as siblings, both should be mounted. Git may not
be available in all sandbox configurations — if `git diff` fails,
skip drift detection and note it in the report.

### Gemini

When invoked via Gemini CLI or Gemini-based agents, the skill is
referenced from `GEMINI.md` (the thin repo-local entrypoint). Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. The same shared validation and render
tooling and procedure apply.

### Cursor

When invoked via Cursor, the skill is referenced from
`.cursor/rules/governance.mdc` (the thin repo-local entrypoint). Resolve
canonical governance from `AGENTS.md` and the workflow authorities after
the runtime entrypoint is loaded. The same shared validation and render
tooling and procedure apply.

### Kilo
